# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

TableGrid is a desktop database GUI client (Tauri 2 + React 19) similar in spirit to DBeaver/TablePlus. It connects to SQLite, PostgreSQL, and MySQL, and lets the user browse/edit table data, alter schemas, run raw SQL, and backup/restore databases. The window uses a custom title bar (`decorations: false` in `src-tauri/tauri.conf.json`) with its own drag/min/max/close controls in `TitleBar.tsx`.

Many user-facing strings, backend error messages, and Rust comments are written in Vietnamese — preserve this convention when touching existing strings/comments.

## Commands

Development requires a native toolchain on Windows: Rust (cargo), a MinGW64 GCC toolchain on PATH (for linking), and Node.js.

- `npm run dev` / `npm start` — run the full Tauri app (spawns Vite dev server + Rust backend with hot reload). Equivalent to `tauri dev`.
- `.\dev-start.bat` — same as above but also sets `PATH` (cargo, MinGW64, node) and `CARGO_TARGET_DIR=C:\cargo-targets\tablegrid`. The target dir is deliberately pointed **outside** the workspace so rust-analyzer doesn't try to watch/index the huge `target/` tree. Use this script (or replicate its env vars) if `cargo`/link errors occur when running `npm run dev` directly.
- `npm run vite-dev` — frontend only, no Tauri/Rust (useful for fast UI iteration, but `@tauri-apps/api` calls will fail/reject since there's no Rust backend listening).
- `npm run build-frontend` — type-check (`tsc -b`) and build the Vite frontend only.
- `npm run build` — full production build via `tauri build` (produces installers/binaries under `src-tauri/target`).
- Rust-only checks: run `cargo check` / `cargo build` from `src-tauri/` (set `CARGO_TARGET_DIR` first as above to avoid a slow first build). Don't run these while `tauri dev` is up — both fight over the same target dir. On this machine cargo has also been seen crashing (`STATUS_ACCESS_VIOLATION`) inside Tauri's build script, which is unrelated to app code.
- `npm run fmt:rust` / `lint:rust` / `test:rust` — rustfmt, clippy (`--all-targets`) and the lib tests. **They `cd src-tauri` rather than passing `--manifest-path`, and the difference is not cosmetic:** cargo discovers `.cargo/config.toml` from the CURRENT DIRECTORY upwards, so run from the repo root with `--manifest-path` it would never read `src-tauri/.cargo/config.toml` — the linker settings and any build flag added there would be silently ignored, with no error. That is the same trap as putting a flag in a `[target.<triple>]` section for a triple nothing builds.
  - They inherit `CARGO_TARGET_DIR`, so they land in `C:\cargo-targets\tablegrid` under `dev-start.bat` and in `src-tauri/target` from a plain shell — the same split `npm run build` and `npm run dev` already have. Both trees are gitignored and both get large (the in-workspace one was 30GB when this was written); deleting either only costs a rebuild.
  - `lint:rust` is at **zero warnings** and worth keeping there — a lint list that is clean is read, and one at 83 is scrolled past. Three lints are switched off at the top of `lib.rs`, each with its argument beside it: `needless_range_loop` (every site indexes something other than the collection it counts — the decode loops walk `0..col_count` to call the driver's `row.get_ref(i)`, and `uniquify_columns` writes back into the slice it walks), `too_many_arguments` (a command's parameter list IS the IPC contract with `dbHelper.ts`) and `manual_async_fn` (`check_server_key` returns `impl Future + Send`, and `async fn` would drop the `Send` a spawned task needs). Do not add a fourth without writing why.
  - Clippy also runs in CI (`.github/workflows/rust-clippy.yml`) but with `continue-on-error: true`, so it only uploads SARIF; `rust.yml` (`cargo build` + `cargo test`) is the actual gate.
  - When clearing warnings, `cargo clippy --fix -- -A clippy::all -W clippy::<one_lint>` keeps the diff to one lint at a time, and `npm run fmt:rust` afterwards — `--fix` leaves the body indented under whatever nesting it just removed. Read the diff rather than trusting it: `--fix` guarantees the result compiles, not that it means the same thing.
- Rust tests: `cargo test --lib` from `src-tauri/` (168 tests). Chúng phủ **hàm thuần** ở các tệp vừa tách ra: `database/{splitter,rows,ident,decode}.rs`, `tx/effect.rs`, `redis_db/cmds.rs`, `datagen/{rng,template,regex,text}.rs`, `compare/{diff,values}.rs`, `stats/table_properties.rs` (đọc ô JSON, đặt tên loại bảng Postgres), `database/introspect.rs` (lọc tên bảng tạm nội bộ), `mcp/exec.rs` (lệnh đọc của AI không ghi được trên SQLite, query chạy mãi bị ngắt đúng hạn, pragma được trả lại) và `credentials/{vault,secret_store}.rs` (seal/open + AAD, dẫn xuất khoá, phân biệt sai-mật-khẩu với tệp-hỏng, luật `__*__`) — phần vault dùng `Params::MIN_M_COST` trong test để kiểm đấu dây chứ không ngồi chờ Argon2 thật. Bốn tệp có test cần một pool sqlx (`ident.rs`) dùng `#[tokio::test]` vì `connect_lazy` spawn task reaper — nó KHÔNG kết nối mạng, chỉ cần một runtime.
- Verifying a **pure** Rust helper without cargo (chỉ còn cần khi build script của Tauri crash): extract the function(s) into a standalone `.rs` file in a temp dir, append a `fn main()` with assertions, then `rustc --edition 2024 -o check.exe check.rs && ./check.exe`. Linking needs the MinGW64 `bin` from `dev-start.bat` on `PATH`, otherwise it fails with `unable to find library -lgcc`. Đây từng là cách duy nhất kiểm `split_sql_statements`; giờ nó đã có `#[cfg(test)]` thật trong `database/splitter.rs`.
- Lint: `npx oxlint` (config in `.oxlintrc.json`). It **exits non-zero on any `correctness` finding**, because the config enables whole categories (`correctness: error`, `suspicious`/`perf`: warn) on top of the two explicit rules (`react/rules-of-hooks`, `react/only-export-components`) — so a new error breaks the check, while the 92 pre-existing **warnings** do not (50 `no-array-index-key` + 42 `no-await-in-loop`, both triaged below — check the BREAKDOWN, not the total, since a legitimate new instance of a triaged group moves the number). Keep the output clean rather than assuming only the named rules run.
  - **`react/react-in-jsx-scope` is `"off"`, and must stay off.** `tsconfig.app.json` sets `"jsx": "react-jsx"` (the automatic runtime), so `React` does not need to be in scope — the rule is inapplicable to this codebase. It also fired *selectively*, which is what makes it worse than useless: only in files importing named hooks (`import { useState } from 'react'`) and never in files that happen to write `import React, { … }`, so it was 65 findings of pure import-style noise drowning the real warnings. JSON takes no comments, which is why the reason lives here.
  - `react/set-state-in-effect` is a correctness error and is disabled **per line, with a reason**, at the four places where an effect is genuinely the right tool (async IPC on mount, image loading, reconciling state against changed props). Before adding another, check whether the value is derivable — `MediaCellPreview` was, and became a `useMemo`; so was `ExportTableDialog`'s preview of a grid SELECTION, whose rows are already in memory (deriving it also deleted the comment reasoning about whether its synchronous `setLoading(false)` beat the microtask-queued `setLoading(true)` — an ordering that no longer exists).
  - `no-underscore-dangle` is `"off"`: it fires on `window.__sqlCompletionDebug` and `__sqlSignatureDisposables`, which are documented debug hooks, and on `__serialized` in `redisDecode.ts`. A double underscore is this repo's marker for "internal / not part of the visible surface", so the rule contradicts a convention rather than catching anything.
  - `oxc/no-map-spread` is `"off"`, and this one is the important off-switch: all ten of its findings were **immutable updates** — `map(c => cond ? { ...c, ...patch } : c)`, defensive copies into React state, derived arrays. Its advice (`Object.assign` in place, or direct property assignment) would mutate state that is still shared, which is the classic "state changed but React did not re-render", and in `aiSessions.ts`/`connectionProfiles.ts` would mutate an object the caller still holds. Following this rule here produces bugs.
  - **`eslint-disable-next-line react-hooks/exhaustive-deps` DOES suppress oxlint's `react/exhaustive-effect-dependencies`** — verified, so the existing documented disables are not silently dead. That backlog is now at **zero**: every site is either a dep that was added or an omission carrying a comment saying why. Keep it there — guessing between the two causes a render loop, so a new finding is worth reading rather than suppressing.
  - `no-shadow` earns its place and is now at **zero**: 33 of its original 43 findings were `t` shadowed by a `.map(t => …)` callback in a file that also calls the translation `t` — the exact hazard the i18n notes below describe. One more was worth the rename on its own (`Sidebar`'s `const schema = await getTableSchema(…)` shadowed the *Postgres schema* named `schema`). Rename the callback rather than disabling; twice during that cleanup the replacement name collided with an existing binding and `tsc` caught it, so check the build rather than trusting the rename.
  - **The two big standing groups are triaged, not ignored — don't re-derive this.** `react/no-array-index-key` (~49) and `eslint/no-await-in-loop` (~40) are left as warnings on purpose, because in this codebase the finding is usually *correct behaviour*:
    - **index keys**: the result grids (`SqlEditor`, `DataGrid`, `DataGeneratorDialog`, import previews) key `<th>`/`<td>` by position **because CLAUDE.md requires it** — duplicate column names collapse otherwise. Append-only logs (redis Console/Profiler/PubSub, `TerminalPanel`, statement lists) and `StructureViewer`'s DDL block (which renders `idx + 1` as the line number) have the index *as* the identity. What is left is the row editors (`CreateTableModal` ×3, `ViewEditorModal`, `CreateRoutineModal`), where deleting a middle row can land focus on the wrong input. Fixing those needs a stable id **added to the state shape** — `key={col.name || idx}` is worse, because clicking "add column" twice gives two rows with an empty name and therefore duplicate keys. Not worth the refactor for a focus glitch; if you do it, add the id.
    - **`await` in a loop**: every site is a sequential DB read — paging (`getTableData(table, page, …)` in `dumpBuilder`, `ExportTableDialog`) or one query per table (`schemaSnapshot`). `Promise.all` there would fire N concurrent queries at the user's production database, which this app avoids on purpose. The rule cannot tell that apart from a slow loop over local data. The same goes for the streamed dump's writes (`writeDump` awaiting its `emit`): chunks must reach the file in order, and awaiting each one is what stops unwritten pages piling up in memory.
- Tests (frontend): `npm test` (Vitest, `npm run test:watch` / `test:coverage`). Only pure helpers are covered — parsers/formatters under `src/utils/__tests__/`. Anything importing `monaco-editor` or `@tauri-apps/api` is not testable in the node environment, which is why SQL text helpers live in `src/sql/statements.ts` (no monaco import) rather than next to the Monaco integration code.

`demo.db` / `demo1.db` at the repo root are sample SQLite databases used for manual testing via the Connection Manager — not fixtures wired into any automated test.

## Architecture

### Process split

- **Frontend** (`src/`): React 19 + TypeScript, built with Vite. All UI, state, and SQL/CSV parsing logic lives here. No direct DB drivers — every DB operation goes through Tauri's `invoke()`.
- **Backend** (`src-tauri/src/`): Rust, exposes `#[tauri::command]` functions as the only bridge to the frontend. Holds the actual DB connections and does all SQL execution, schema introspection, and file I/O (export/backup/restore).

The frontend never talks to a database directly — `src/utils/dbHelper.ts` is the single wrapper around every `invoke()` call and is the de facto contract between the two sides. When adding a new backend capability, add the `#[tauri::command]` in the right `database/commands/*.rs`, register it in the `generate_handler!` list in `app/handlers.rs`, then add a corresponding method to `dbHelper`.

**Every `#[tauri::command] async fn` obeys two rules, and breaking either one crashes the RELEASE build at the first call while `tauri dev` stays perfectly happy.** All 143 of them follow both; a new one must too.

1. **Never take `tauri::State<'_, AppState>`.** Read the state with `crate::state::require_state()?` instead. That parameter carries a lifetime, so the command's future is not `'static`; Tauri can only `spawn` a `'static` future onto the async runtime, and anything else it builds *and runs* on the calling thread — the main thread, whose stack Windows reserves at **1MB** (Linux and macOS give 8MB, which is why this is invisible on those). `AppState` is `Clone` over an `Arc`, so `require_state()` costs one refcount bump.
2. **Wrap the body in `Box::pin(async move { … }).await`.** `#[tauri::command]` expands to `async move { let result = $path(args); … kind.future(result).await }`, and `result` lives across an `.await`, so the command's whole future is a *field* of that block's state machine. Creating the block allocates the struct — **not running yet is not the same as not occupying space**. Boxing puts the state machine on the heap and leaves the command's own future holding its arguments and a pointer.

The two compose and neither replaces the other: rule 1 decides *which thread* runs the body, rule 2 decides *whose stack* the state machine lands on. `connect_db` broke rule 1 and `get_databases_list` broke rule 2, and each produced the same symptom — `STATUS_STACK_OVERFLOW` (0xc00000fd) on `thread 'main'`, at launch or on the first connection, with no console to print it in a packaged build.

Debug never inlines the way `lto = "fat"` + `codegen-units = 1` does, which is why this is a release-only failure and why `tauri dev` cannot catch it. Reproduce with `npx tauri dev --release` — the same profile, but run from a terminal so the crash line is visible. Do not diagnose it by reasoning about which function looks big: five hypotheses were wrong before a trace (thread name + address of a local, appended to a file per line, since a windowed build has no stderr) named the real one in a single run.

### Backend (`src-tauri/src/`)

**Bản đồ module** (chi tiết từng phần ở các mục ngay bên dưới). Mỗi tệp làm **một** nhiệm vụ; tệp lớn đã được tách thành thư mục cùng tên, và `mod.rs` của thư mục chỉ chứa `mod` + `pub use` (không logic). Kế hoạch và lý do từng quyết định: `docs/backend-module-split-plan.md`.

- `app/` — vòng đời Tauri, không thuộc về database nào:
  - `app/setup.rs` — chạy một lần lúc khởi động: vật liệu kính của cửa sổ, và park `AppHandle` cho `tx/` + `state/` (hai tầng nhận `&DbConnection` mà không nhận `AppState`).
  - `app/handlers.rs` — **danh sách `generate_handler!`**. Thêm một command mà quên khai ở đây thì frontend gọi sẽ lỗi runtime "unknown command"; compiler không bắt được.
  - `app/run.rs` — `Builder` của Tauri: plugin, `manage(AppState)`, nối `setup` và `handlers`.
  - `app/shell.rs` — `open_url`, `set_app_window_size`. `app/ai.rs` — `ai_chat` (stub).
- `lib.rs` — **chỉ** khai báo module, cộng hai re-export giữ nguyên đường dẫn cũ (`tablegrid::run`, `crate::AppState`). Bootstrap của Tauri nằm ở `app/run.rs`, cạnh hai mảnh của chính nó là `setup.rs` và `handlers.rs`.
- `state/` — mọi state còn sống: `app.rs` (`AppState`, thứ Tauri `manage()`) và registry kết nối (`ids.rs` danh tính, `server.rs` `ServerHandle`, `entry.rs` một mục, `ctx.rs` `ConnCtx`/`RedisCtx`, `registry.rs` `ConnRegistry`, `app_handle.rs` handle park). Khối comment đầu `state/mod.rs` giải thích ba quyết định của `docs/multi-connection-plan.md` §4.
- `database/` — mọi thứ nói chuyện với một database SQL:
  - Tầng nền: `conn.rs` (`DbConnection`/`DbKind`/`Exec`), `dsn.rs` (dựng URL + `apply_ssh_tunnel`), `iam.rs`, `decode.rs` (hai macro decode + bind tham số), `rows.rs` (`uniquify_columns` và bạn bè), `ident.rs` (`quote_ident`/`qualified`/`sql_str`/`sql_literal`), `read_only.rs`, `timeout.rs`, `splitter.rs` (`split_sql_statements`).
  - `database/exec/{raw,bound,stream}.rs` — ba funnel thực thi.
  - `database/commands/` — một nhóm lệnh một tệp: `connection`, `catalog`, `row_read`, `row_write`, `query`, `table_schema`, `table_alter`, `table_ddl`, `ddl_extras`, `databases`, `status`, `restore`, `stubs`, và `objects/{listing,triggers,sequences,routines,views,partitions,constraints}.rs`.
  - `status.rs` nuôi cụm trạng thái trên thanh tiêu đề, và `TitleBar.tsx` poll `get_connection_status` **mỗi 6 giây** — nên chỉ `SELECT 1` (đo latency) được chạy mỗi nhịp. Năm trường còn lại (version / user / database / cipher / TLS) là hằng số của phiên và được cache ở `ConnEntry.session_info` (`state/entry.rs`), probe một lần trong `probe_session_info`; trên MySQL riêng phần này là **ba** round trip (`SELECT VERSION(), CURRENT_USER(), …` cộng một `SHOW SESSION STATUS` cho mỗi `Ssl_cipher`/`Ssl_version`), tức ba câu vô ích mỗi 6s trong general log của server nếu không cache. Cache theo entry chứ không theo server vì `database` là một trong các trường, và bị xoá ở đúng hai chỗ — `ConnRegistry::replace_conn` và `set_db`, hai đường DUY NHẤT đổi được pool hoặc database dưới một `conn_id` mà không mint id mới (IAM refresh trả lời y hệt, nhưng restore replay một dump có `USE <db>` thì không). Nhánh Redis trả lời từ `RedisCaps` probe lúc connect nên không dùng cache này. Đừng thêm truy vấn mới vào `get_connection_status`: mọi thứ đặt ngoài `probe_session_info` sẽ chạy 10 lần mỗi phút cho mỗi kết nối đang xem.
- `tx/` — chế độ commit thủ công: `effect.rs` (phân loại câu lệnh, **thuần**), `session.rs` (state machine), `route.rs` (định tuyến + ba funnel song sinh), `commands.rs`.
- `compare/` — so sánh hai database: `side.rs`, `meta.rs`, `ident.rs`, `read/{mysql,pg,sqlite}.rs`, `diff.rs`, `sync_sql.rs`, `schemas.rs`, `data_overview.rs`, `data_rows.rs`, `values.rs`, `script.rs`.
- `datagen/` — sinh dữ liệu test: `rng.rs`, `template.rs`, `regex.rs`, `text.rs` (bốn tệp **thuần**), `spec.rs`, `ident.rs`, `column.rs`, `meta.rs`, `suggest.rs`, `writer.rs`, `commands.rs`.
- `redis_db/` — trình duyệt Redis: `config.rs`, `caps.rs`, `conn.rs`, `value.rs`, `session.rs`, `keys/{scan,read,write,manage}.rs`, `types/{hash,list,set,zset,stream,json}.rs`, `admin.rs`, `slowlog.rs`, `live.rs`, `analyze.rs`, `transfer.rs`, `cmds.rs`. **Không** đặt tên module là `redis`: nó sẽ trùng tên với crate `redis` và làm `use redis::aio::…` thành lỗi E0659 ở mọi tệp.
- `terminal/{local,ssh}.rs` — hai backend của bảng Terminal. Chúng nằm chung thư mục vì dùng CHUNG một giao thức message, nên frontend chỉ có một component cho cả hai; giao thức được ghi ở đầu `terminal/mod.rs`.
- `credentials/{aws_iam,oauth,secret_store,vault}.rs` — lấy và cất thông tin xác thực. Bốn tệp này không dùng chung code, chúng dùng chung một **mối quan tâm**: gom lại để câu hỏi "app giữ bí mật ở đâu" có đúng một chỗ trả lời.
  - **`secret_store.rs` là funnel DUY NHẤT của mọi lượt đọc/ghi bí mật**, và chính điều đó khiến Master Password là một cú tráo phía dưới chứ không phải một thay đổi lan tới frontend: `secretFields.ts`, `persistProfiles`, `connectProfile.ts` không đổi một dòng nào. Mặc định nó ghi vào kho HĐH; khi người dùng bật mật khẩu chính thì nó định tuyến sang `vault.rs`.
  - **Ngoại lệ `is_internal()` (tên profile bắt đầu bằng `__`) là thứ chịu lực**, đừng bỏ. Khoá của chính app — bearer token + khoá nhật ký MCP (`__mcp__`), device key của vault (`__vault__`) — LUÔN ở lại keyring, vì hai lý do: `audit_file::init` đọc khoá của nó ngay trong `app/setup.rs`, tức trước khi ai kịp gõ mật khẩu chính; và device key mở kho thì không thể nằm trong chính cái kho nó mở.
  - `vault.rs` — một tệp `vault.json` ở app data dir: header Argon2id (salt + m/t/p **ghi vào tệp**, nên nâng cost sau này vẫn mở được kho cũ) + `check` là một hằng số được seal, đó là thứ duy nhất phân biệt "sai mật khẩu" với "tệp hỏng" — cả hai đều là một lỗi AEAD, và đoán giữa chúng là cách báo "sai mật khẩu" cho một tệp bị cắt cụt. Mỗi entry seal bằng AES-256-GCM với **AAD là chính account key** (`<profile>:<field>`): bê một blob từ field này sang field khác là nó không mở được nữa, nếu không thì tráo hai entry trong tệp là không phát hiện được và một profile lặng lẽ kết nối bằng mật khẩu của profile khác. Khoá dẫn xuất nằm trong `Zeroizing` ở RAM của Rust, **không bao giờ đi qua IPC** — frontend chỉ thấy ba boolean.
  - Bật/tắt đều **ghi đích trước, xoá nguồn sau**, nên một lần gián đoạn để lại bí mật ở CẢ HAI chỗ chứ không mất. Ghi tệp là `write .tmp` rồi `rename` — crash giữa chừng mà không có bước đó là mất sạch credential đã lưu.
  - Bốn lệnh cần Argon2 (`vault_enable/unlock/disable/change_password`) là `async fn` + `Box::pin` + `spawn_blocking`: một `#[tauri::command]` KHÔNG async chạy trên main thread, mà 64 MiB × 3 pass tốn ~0.2s, đủ để cửa sổ đứng hình.
  - **Auto-unlock chỉ xảy ra ở `init()` lúc khởi động, và chỉ khi cờ `relock` trong tệp là false.** Cờ đó được bật mỗi lần khoá CÓ CHỦ Ý (nút "Khoá ngay" hoặc hết giờ rảnh) và chỉ được xoá bởi một lượt `vault_unlock` đi qua mật khẩu — đường DUY NHẤT chứng minh người dùng biết mật khẩu. Nó chính là thứ để "ghi nhớ trên máy này" và "khoá khi rảnh" sống chung: ghi nhớ nghĩa là không hỏi lúc KHỞI ĐỘNG, còn khoá có chủ ý thì vẫn hỏi, kể cả sau khi restart. Thiếu cờ này thì device key nằm sẵn trong keyring khiến mọi lần khoá đều đi vòng qua được bằng cách thoát rồi mở lại app — và câu trả lời trung thực lúc đó là phải **chặn** hẳn tuỳ chọn auto-lock, tức giết một tính năng để che một lỗ hổng. Ghi cờ thất bại thì **fail closed**: xoá luôn device key. `relock` khai `#[serde(default)]`, vì một `vault.json` viết trước khi có trường này vẫn phải mở được.
- `ssh/{auth,tunnel}.rs` — `auth.rs` là **đường xác thực SSH duy nhất**, dùng chung bởi tunnel và `terminal/ssh.rs`; `tunnel.rs` là phần chuyển tiếp cổng. `terminal/ssh.rs` KHÔNG nằm ở đây: nó thuộc `terminal/` cùng bản local, vì giao thức message chung giữa hai bảng terminal mới là ràng buộc dễ vỡ — SSH chỉ là đường truyền của nó.
- `stats/` — thống kê dung lượng/số dòng: `cells.rs`, `system_dbs.rs`, `probe.rs`, `database.rs`, `all_databases.rs`, `sizes.rs`, `row_count.rs`, `table_properties.rs`.
  - `table_properties.rs` (`get_table_properties`) là nguồn duy nhất của tab **Properties**. Nó đọc qua `execute_raw_sql_generic` chứ không qua driver row: funnel đó đã định tuyến sang kết nối được ghim khi có transaction thủ công, và đó là cách DUY NHẤT nhìn thấy một bảng tạm theo phiên. Mọi truy vấn phụ đều `.ok()`-dung thứ (thiếu `dbstat`, thiếu `sqlite_sequence`, chưa có dòng trong `pg_stat_all_tables`) — thiếu một số liệu phụ không được làm trắng cả bảng. DDL của Postgres dựng lại tại chỗ thay vì gọi `get_table_definition`: lệnh đó qualify theo schema của kết nối nên không bao giờ thấy được bảng nằm trong `pg_temp_N`.

- `database/` — cốt lõi của app. Những điều cần biết trước khi sửa:
  - `DbConnection` enum unifies `rusqlite::Connection` (wrapped in `Arc<Mutex<_>>`), `sqlx::PgPool`, and `sqlx::MySqlPool` behind one type. Every open connection lives in `state::ConnRegistry` (`AppState.connections`), keyed by `conn_id`; **there is no "active connection"** — every connection-bound command takes a `conn_id` argument. What the connections of one *server* share sits on an `Arc<ServerHandle>`: `db_type`, the connection config (`last_config`) and the SSH tunnel. `last_config` is what lets `restore_backup` reconnect transparently when a dump issues `USE <db>` (MySQL), and what `compare/` and the deep scan build their short-lived pools from.
  - The universal pattern in every command: lock `state.db_manager`, clone the connection handle out (`Arc`/pool clones are cheap), and **drop the lock before any `.await`** — `MutexGuard` is not held across awaits. Follow this pattern for new commands.
  - `execute_raw_sql_generic()` is the common dispatcher that runs a raw SQL string against whichever backend is active and normalizes the result into `{ columns, data }` JSON. Most commands build a SQL string and funnel it through this function rather than talking to `rusqlite`/`sqlx` directly.
  - SQL is assembled via string formatting (not parameterized queries) throughout — identifiers/values are manually quoted and escaped (e.g. `.replace("'", "''")`). This is inherent to a "raw DB browser" tool where table/column names are dynamic, but be careful preserving the escaping when touching this code.
  - Quoting is inconsistent by design across dialects: MySQL uses backticks, Postgres/SQLite use double quotes; several code paths build with backticks and `.replace("`", "\"")` for Postgres. Check the surrounding dialect-switch (`match db_type`/`match &conn_type`) before changing quoting logic.
  - `generate_alter_sqls()` translates a structured diff payload (added/dropped/renamed/modified columns, indexes, foreign keys) from the frontend's schema editor into a list of `ALTER TABLE`/`CREATE INDEX`/etc. statements, branching per dialect. `alter_table_schema` executes them; `preview_alter_schema` returns the same SQL as text without running it (used by the UI's "preview SQL" step before committing schema changes).
  - `split_sql_statements()` is the splitter used by `execute_multi_query` and `execute_query_stream` (i.e. "run all statements" from the SQL editor). It tracks quoting/escapes, `--`/`#`/`/* */` comments, Postgres `$$…$$` / `$tag$…$tag$` bodies, and MySQL's client-side `DELIMITER <token>` command (whose lines are consumed, never sent to the server). It also knows **trigger bodies**: while the delimiter is still `;`, a statement starting with `CREATE … TRIGGER` **and containing a `BEGIN` word** only ends at the `;` that directly follows `END` (`trigger_stmt_incomplete()` / `insideTriggerBody()`) — that is `sqlite3_complete()`'s rule, and SQLite needs it because it has no `DELIMITER`, so an exported trigger used to come back as a truncated `… BEGIN UPDATE t SET …;` and killed the whole restore. Requiring `BEGIN` is what keeps a Postgres trigger (`… EXECUTE FUNCTION f();`) and MySQL's single-statement form from swallowing the rest of the dump. Its frontend twin is `src/sql/statements.ts` — **keep the two in sync**: the editor decides what Ctrl+Enter runs and what gets highlighted, the Rust one decides what actually executes, and a mismatch means the user runs something other than what was highlighted.
  - `restore_backup()` replays a multi-statement `.sql` dump statement-by-statement, filtered to the selected tables, inside a transaction — three branches, **each on one connection it holds itself and none through a funnel**: MySQL (acquired connection + `SET FOREIGN_KEY_CHECKS`), Postgres (acquired connection, `BEGIN` then `SET CONSTRAINTS ALL DEFERRED`, a savepoint around every session-level statement so a rejected `SET` cannot poison the transaction with 25P02), SQLite (`PRAGMA foreign_keys OFF` on the handle). Postgres used to send `BEGIN` through `execute_raw_sql_generic`, which only held together because `should_route` opened a manual-transaction session on the caller's `conn_id` — i.e. the restore became the user's transaction. `cancel_restore(conn_id)` raises a flag checked between statements; the run rolls back and answers `cancelled: true` (on MySQL, DDL already run stays committed). It now **reuses `split_sql_statements()`** (the same splitter as the SQL editor) instead of the two inline `;`-only scanners it used to have, so `DELIMITER` blocks and `$$…$$` bodies survive — a `mysqldump --routines` file with triggers/procedures/functions replays correctly. After filtering, every `CREATE VIEW` is moved to the **end** of the list (stable partition, so their relative order survives). `CREATE VIEW` is validated when it runs, and dumps interleave views with tables alphabetically — sakila's `actor_info` sits right after `actor`, long before the `film` it selects from, so the whole restore died on MySQL 1146. The export side now writes views last, but dumps that already exist (and other tools' dumps) can't be fixed retroactively, so the runner has to tolerate the wrong order. Only `CREATE VIEW` moves: `DROP VIEW` staying put is harmless, and moving anything else could change what the dump means (a dump that INSERTs through an updatable view would break). The pre-filter that builds this list runs over **every** statement before the progress channel sends `start`, so anything quadratic in it shows up to the user as a frozen "preparing" bar: `TableMatcher` compiles **one** alternation regex for the whole restore (the old code compiled `\b<name>\b` per statement × per table — 50k × 22 ≈ 1.1M `Regex::new()` calls, measured at 20.3s vs 3ms), and `upper_head()` uppercases only the first 32 bytes instead of copying every multi-megabyte INSERT. Three helpers drive the per-statement decision: `is_session_level_stmt()` (statements that always run and whose failure is *not* fatal: `USE`, `SET …`, `CREATE DATABASE/SCHEMA` — a dump from another dialect will have `SET` lines the current server rejects), `stmt_mentions_table()` (word-boundary match against the selected tables), `use_db_name()` (target of `USE` for the post-restore reconnect). Deliberately **not** in the always-run list: `DROP DATABASE`/`DROP SCHEMA`, so importing a dump that starts with `DROP SCHEMA x` never wipes a schema the user didn't select. The `run_all` flag turns the table filter off entirely, and exists because that filter is **wrong** for a dump the app built itself: `TableMatcher` cannot see a table's name in every statement belonging to it — Postgres' `CREATE SEQUENCE IF NOT EXISTS film_film_id_seq;` holds no whole word `film` (an underscore is a word character), so filtering a generated dump drops the sequence and the `CREATE TABLE film (… DEFAULT nextval(…))` behind it fails. Only the copy-database path passes it (with an empty `tables`); a user-supplied file must keep the filter, since it is the only thing between "restore these four tables" and "replay the whole file".
  - **MySQL + prepared statements:** `sqlx::query()` uses the prepared-statement protocol, and MySQL rejects `CREATE`/`DROP TRIGGER|PROCEDURE|FUNCTION|EVENT` there with error **1295** (`This command is not supported in the prepared statement protocol yet`). Anything that may execute routine DDL must go through `sqlx::raw_sql()` (text protocol) — `restore_backup` does so unconditionally on MySQL, while `execute_raw_sql_generic` and `execute_query_stream` fall back to it (see `is_mysql_unprepared_error()`) so the SQL editor can create triggers/procedures too. Note MySQL also **implicitly commits on DDL**, so the transaction wrapped around a restore does not roll back already-created objects.
  - **Duplicate column names / `uniquify_columns()`:** every result row is shipped as a JSON object keyed by column name (`{ columns: [...], data: [{col: val}] }`), so two columns with the same name would collapse — `serde_json::Map::insert` overwrites and all but one value is lost with no error. `SELECT *` across a few joins hits this instantly (sakila's `film JOIN inventory JOIN store JOIN address JOIN city` returns five `last_update` and three `film_id`). Two rules, and **both** are needed at every one of the ~10 row-building sites: (1) run `uniquify_columns(&mut columns)` right after the column-name list is built and before any row is assembled, so repeats become `last_update (2)`, `last_update (3)`, … and the `columns` array the frontend receives carries the same suffixed names its `row[col]` lookups will use; (2) on Postgres/MySQL decode cells **by index** (`decode_pg_cell!(&r, i)`), never by name — `sqlx::Row::try_get(name)` resolves to the *first* column with that name, so a name-keyed loop returns that same first value for every repeat. The `decode_pg_cell!`/`decode_mysql_cell!` macros deliberately take an untyped `$col` so both a `&str` and a `usize` work; the `&str` form is only for hand-written introspection queries with known-unique aliases. The frontend needs no matching change, but `SqlEditor.tsx`'s result grid keys its `<th>`/`<td>` by **position**, not column name, because a stale/older backend can still send repeats.
  - `commit_changes` (the grid's "Save") runs its statements inside **one** transaction via `Exec` — one connection for the whole batch, `BEGIN`/`COMMIT`, `ROLLBACK` on the first failure. It cannot be wrapped around `execute_raw_sql_generic` instead, which acquires a new pooled connection per call. The batch is DML-only on purpose: adding DDL would make MySQL commit implicitly and defeat the rollback. When a **manual** transaction is already open it joins that one instead, leaving the commit point to the user.
  - **Postgres object kinds.** `get_table_definition` branches on `pg_class.relkind` before it builds anything: `'v'`/`'m'` return `CREATE [MATERIALIZED] VIEW … AS pg_get_viewdef()`, everything else falls through to the hand-built `CREATE TABLE` (columns + NOT NULL + DEFAULT + PK). Without that check it emitted a `CREATE TABLE` for every **view** too, so a re-imported Postgres dump grew real tables shadowing its views. Materialized views also need `pg_class.relkind = 'm'` to be listed at all — `information_schema.tables` does not contain them (not in the SQL standard), which is why they were invisible in the sidebar, the export dialog and compare; `get_tables` and `get_database_objects` both UNION them in as `VIEW`. A matview needs no `REFRESH` in a dump because `CREATE MATERIALIZED VIEW` populates on the spot and the dump writes it after the tables it reads, but its DROP must say `MATERIALIZED` — `dumpBuilder` detects that from the DDL text rather than threading a kind through.
  - **Postgres schema selection lives in `ConnEntry.current_schema`, not in command arguments.** One `conn_id` is one `(server, database)`, so it is also one current schema — the schema's home moved from a single global into one entry per connection when multi-connection landed. `connect_db` seeds it from `SELECT current_schema()` (`probe_pg_schema`), `open_database` probes it for the connection it mints (each database has its own schemas), `disconnect_db` drops the entry with it, and `set_current_schema` (the Sidebar picker) sets it after checking the name exists. All of them return the effective schema, and the frontend must read it from there rather than from its own picker state: it is part of the localStorage scope (`scopeKey`), so a value the backend disagrees with keys tabs wrongly. `list_schemas` returns `[]` on MySQL/SQLite, which is how the UI decides whether to show the picker at all. Three helpers carry it: `ConnCtx::schema()` (what every call site reads — it defaults on the way out, so a site can no longer forget to default and silently query `public`), `pg_schema_of()` (where that `public` default is spelled, once), `sql_str()` (escape for a `nspname = '…'` literal), and `qualified()` — the twin of `compare/ident.rs` and of `datagen/`'s own copy, which only qualifies on Postgres so MySQL/SQLite output is unchanged. `datagen/` gets the schema from `active_conn()` (which already returned the dialect) because the five functions needing it are internal, not commands. **When adding a path that builds SQL from a table name, qualify it** — the write paths carry no `'public'` to grep for, so a missed one silently targets `public`, and `get_primary_key_columns` reading a different schema than `commit_changes` writes to is a wrong `WHERE`, i.e. wrong rows changed rather than an error. `docs/postgres-schema-support-plan.md` §4.2 lists every call site. Emitted DDL is deliberately **not** qualified so a dump can be restored into a differently-named schema; `dumpBuilder`'s header carries `CREATE SCHEMA IF NOT EXISTS` + `SET search_path` instead (only when the schema is not `public`, so ordinary dumps are byte-identical to before). One thing that escapes it: `pg_get_indexdef()` is Postgres's own output and always includes the source schema.
  - MySQL **scheduled events** come from `information_schema.EVENTS` (in `get_database_objects`, empty on the other two dialects) and their DDL from `SHOW CREATE EVENT` via `get_object_definition(kind = "event")`. The dump writes them in the same `DELIMITER $$` block as routines and triggers, because an event body (`DO BEGIN … END`) carries its own `;`.
  - `ai_chat` vẫn là stub echo lại prompt; UI "AI Copilot" (`AiAssistant.tsx`) chưa nối vào model thật. Nó nằm ở `app/ai.rs`, không ở `database/`, vì nó không chạm database nào.
  - **Ba stub chết đã bị xoá** (`export_table`, `import_dbeaver`, `restore_backup_old`) cùng `export.rs` và dependency `flate2`. Dump được dựng ở frontend (`utils/dumpBuilder.ts`), còn `import_new_table`/`import_table_data` là code THẬT — chúng nằm ở `database/commands/row_write.rs`, đừng nhầm với đám stub cũ.
- `tx/` — **manual transaction mode** (auto-commit toggle, Commit/Rollback, isolation level, savepoints), driven by `TxControl.tsx` on the title bar. The things to know before touching anything that runs SQL:
  - **A transaction belongs to the connection, not to a tab.** Sessions are a `HashMap` keyed by `conn_id` (`TX_REGISTRY` in `tx/session.rs`), so there is one session per open connection and two tabs on the same connection share it. That is why the control lives on the title bar scoped to one connection (`TxControl` takes it as a `connId` prop and **drops `tx-state-changed` events carrying any other one**), rather than each tab's toolbar owning a transaction. `tx_status` therefore takes a `conn_id`; the one question that is not per-connection is `tx_any_pending()`, which the window-close guard asks because closing the window kills every session at once.
  - **The naming here is constrained by CodeQL, and the constraint is not obvious.** The accessor is `conn_scope_id()` and the map is `TX_REGISTRY`/`ConnScopeId` — **do not put `session`, `key` or `uuid` back into any of those names.** CodeQL's sensitive-name heuristic (`SensitiveDataHeuristics.qll`, `maybeAccountInfo`) matches `session.?(id|key)` and any `uuid` substring, which makes the function a taint *source*; because the returned `&str` borrows `conn.id` while the same `conn` carries the DB handle in `conn.kind`, the analysis (which does not separate two fields of one struct) then reports `Exec::run` and `sqlite_raw` as `rust/cleartext-storage-database` — high severity, and a false positive every time: `mint_id()` is a random v4 UUID, never derived from the config, and the id never enters a SQL string. Renaming `session_key` -> `session_id` was tried and **could not work**, since `id` and `key` are alternatives inside the same group of that regex. The domain word "session" is fine everywhere it does not sit next to `id`/`key` — `Session`, `session_for`, `tx/session.rs` are all clean. `terminal/{local,ssh}.rs` still take a `session_id` **parameter**: that is the IPC contract with the frontend, it reaches no database sink, and renaming it would break `dbHelper`.
  - **Every SQL path must ask the session.** `should_route()` is checked at the top of `execute_raw_sql_generic`, `run_bound_query` and `stream_one_statement` — **a new execution path must do the same**. Routing only some of them means a grid refresh reads through a different pooled connection and cannot see the uncommitted rows, which reads to the user as lost data. Routing is by design a *global* lookup (a module-level `static`, not `AppState`): those funnels receive a `&DbConnection` and no `AppState`, and there is only ever one session to find.
  - This is why `sqlite_raw` / `pg_raw` / `mysql_raw`, `*_bound` and `*_stream` exist as separate functions: the identical body runs whether the connection came from the pool or from the pinned session. Duplicating them would duplicate the two rules every row-building site must follow (`uniquify_columns` first, decode **by index**).
  - **Auto-commit OFF issues `BEGIN` from the client**, JDBC-style, because Postgres has no server-side autocommit flag. A hand-typed `BEGIN` also opens a session (`should_route` returns true for it) — before this existed it went to a pooled connection and did nothing but leave that connection *idle in transaction*.
  - `tx_effect()` classifies every statement so the pending counter cannot lie: it catches the user's own `COMMIT`/`ROLLBACK`/`SAVEPOINT` and MySQL's **implicit commit on DDL**. It reads only the first 4 tokens — it runs on every statement, including bulk INSERTs whose text is megabytes. Postgres's aborted state (`25P02`) is detected here too and surfaced as a boolean, never compared as text on the frontend.
  - `is_write_stmt()` decides what the counter counts. A `SELECT` **does** open the transaction (that is how you read back what you just wrote, and the only way an isolation level means anything) but is **not** counted — the number next to Commit promises "this many changes are waiting". Unknown shapes (`WITH …`, `CALL …`) count as writes: over-reporting costs a needless rollback, under-reporting loses data.
  - The session also keeps the **SQL text** of those write statements (`pendingSql`) for the pending-changes dialog, capped per statement and in total, with a `sqlTruncated` flag rather than silently showing less. Each savepoint records the counter value at the time, so `ROLLBACK TO` rewinds both the count and the log exactly instead of guessing.
  - **SQLite is not pinned**: `DbConnection::Sqlite` is already one shared handle, i.e. already one session. Only the state machine applies, and the isolation-level select carries `DEFERRED/IMMEDIATE/EXCLUSIVE` instead of isolation levels.
  - **A write path outside the three funnels must ask `use_session()`, never `is_open()`.** A transaction does not exist until its first statement runs, so a command that checks `is_open()`, finds `false` and takes its own connection commits behind the user's back while the mode still says "manual" — that was a real bug in `commit_changes` (the grid's Save), `drop_table` and `truncate_table`. `run_fk_wrapped()` is the shared shape for "a couple of statements on one connection, with FK checks optionally off around them" and gets this right.
  - Lifecycle, all deliberate: `connect_db`/`disconnect_db` roll back and reset; **`open_database` refuses nothing** — it *adds* a pool under a new `conn_id` instead of swapping the pool under a live one, so a transaction open on the current database keeps running while the user works in another (this is why `switch_database`, which had to refuse whenever the connection held uncommitted work, was deleted rather than fixed); `restore_backup` and `generate_data` refuse whenever manual mode is on at all, since they commit periodically by design and so can never join the user's transaction; the IAM refresh task skips a pool swap while one is open. The frontend blocks window close via `onCloseRequested`.
  - State reaches the UI as a `tx-state-changed` **event** (the `AppHandle` is parked in the module at setup), not as a field added to every command's response.
- `compare/` — compares **two** databases (structure and data), driven by `DbCompareDialog.tsx`. The one thing to understand before touching it: a side may point at a database no connection is open on, so each is resolved separately in `resolve_side()` — it **reuses the connection identified by `conn_id`** when the side names the same place (no re-auth, which matters for AWS IAM tokens) and otherwise opens a short-lived pool from that server's config with the database/file overridden, exactly like `get_all_databases_stats`' deep scan. Every ad-hoc pool is built with `DbConnection::adhoc`, so `ConnId::Adhoc` makes it **structurally impossible** for `should_route` to pin it as the user's transaction session — that was a real bug once (§0 of `docs/multi-connection-plan.md`), and it is now a property of the type rather than a rule to remember. Ad-hoc pools are closed by `Resolved::close()` before the command returns; SQLite is opened `SQLITE_OPEN_READ_ONLY` so a mistyped path can never create an empty file. Metadata goes through `execute_raw_sql_generic` (now `pub(crate)`, along with `apply_ssh_tunnel`/`apply_iam_password`) rather than re-decoding driver cells. Three commands: `compare_schemas` (per-table/column/index/FK diff + sync SQL), `compare_data_overview` (row counts per table, cheap triage), `compare_table_data` (row-level diff by key + INSERT/UPDATE/DELETE script). Notes: type comparison is normalized (`norm_type` folds `int(11)`/`INT` and `character varying`/`varchar` so MySQL 5.7-vs-8 or MySQL-vs-Postgres doesn't report noise, while lengths still count); `values_equal` only loosens number-vs-numeric-string (`DECIMAL` arrives as a string from sqlx) and compares two strings exactly, so a real difference is never hidden; every `DROP`/`DELETE` is emitted **commented out** unless `includeDrops` is set, and a changed index/FK comments its DROP *and* CREATE together so a half-applied script can't happen. **Language split** (deliberate): errors and the `warnings` array are Vietnamese and translated via `backendErrors.ts` (`dbHelper` maps `warnings` too — `translateResultErrors` only covers `message`/`error`), but comments inside the generated SQL script are **English**, because that script is an artifact the user pastes into a migration/CLI, not UI text.
- `datagen/` — bulk **test-data generation** (dbForge-style Data Generator), driven by `DataGeneratorDialog.tsx`. Four commands: `get_generation_targets` (tables/columns + a *suggested* generator per column + the FK-safe insertion order), `preview_generated_data`, `generate_data` (progress + cancel over a `Channel`), `cancel_data_generation`. The decisions worth knowing before touching it:
  - **Values are produced only in Rust — there is no TS twin, on purpose.** Preview runs the same code path as the real run (minus the writes), so what the user sees is what gets inserted. One deliberate exception: a FK column whose parent is still empty would preview as a column of NULLs (the parent is only filled during the run), which reads as a broken generator — `estimate_fk_pool` therefore shows the keys the parent is *about* to get (replaying the parent's generator, or continuing from `MAX(key)` for an auto-increment parent) and the result carries a warning saying the values are an estimate. The preview call sends the **whole** spec, not just the previewed table, because that estimate needs the parent's spec. `split_sql_statements` ↔ `sql/statements.ts` and the Rust error literals ↔ `backendErrors.ts` are already two hand-synced pairs; a third one existing only for preview would drift silently. `utils/dataGenHelper.ts` therefore holds spec plumbing (labels, option-field descriptions, validation) and no generators — its one small twin, `templateSpace`, feeds a warning and never generation.
  - **Determinism**: a seeded xoshiro256\*\* written here (~30 lines) — no `rand`/`fake`/`rand_regex` crate, no OS entropy, no clock, so the same spec + seed replays byte-identically. Each column draws from its **own** substream (`mix_seed(seed, table, column)`); one shared stream would make editing column 3 shift the values of every later column and the preview jump on every keystroke. `regex` (the crate) can only match, not sample, so the supported regex **subset** is parsed and sampled by hand (`parse_regex`/`sample_regex`), and anything outside it (`(?…)`, backreferences, anchors, `{n,m}` over 64) is rejected while the column is configured rather than at row 1,000,000.
  - **Writing**: one dedicated connection per run (`Exec`), because `execute_raw_sql_generic` acquires a *new* pooled connection per call, so `BEGIN` / `SET FOREIGN_KEY_CHECKS` issued through it would land on a different session than the INSERTs. Batched multi-row INSERT (500 rows, less for wide tables) with a periodic COMMIT, **plus a COMMIT at the end of every table** — a FK column reads its parent key through `execute_raw_sql_generic`, i.e. from another pooled connection, which cannot see rows still uncommitted in ours, and an auto-increment parent key exists *only* in the database (the column is generated with `skip`), so without that commit generating a parent and its child in one run always failed. FK values are the union of "what the parent table holds" and "what this run generated for it" (the latter covers a reference cycle, where the parent is generated after the child); there is deliberately no "only existing values" switch, because no honest description of it survives those two requirements. Constraint-disabling order is dialect-specific and not interchangeable: SQLite `PRAGMA foreign_keys` is a **no-op inside a transaction** (so it goes first), Postgres `SET CONSTRAINTS` is only valid **inside** one (so it goes after BEGIN, and again after every periodic commit). "Delete existing rows" uses `DELETE`, not `TRUNCATE`, because MySQL implicitly commits on DDL and would strand what the transaction already wrote.
  - Error messages name `table.column` so none of them needs an outer wrapper — a wrapped Vietnamese message could not be matched by `backendErrors.ts`, whose new `nested` flag exists for the one genuinely nested case (a regex parser error inside "Regex của cột '…' không hợp lệ: …").
  - Pure helpers (PRNG, template/regex expanders, Luhn, topo-sort, `type_family`, MySQL enum parsing) are verified with the standalone-`rustc` trick described above rather than by a cargo test.
- `ssh/` — SSH, hai nhiệm vụ tách rời. `auth.rs`: `connect_and_auth()` (password hoặc private key; `check_server_key` chấp nhận tất cả — không có `known_hosts`), dùng chung với SSH terminal. `tunnel.rs`: `SshTunnel::open()` bind `127.0.0.1:0` và bơm mỗi socket nhận được qua một kênh `direct-tcpip`. `database::apply_ssh_tunnel()` là entry point mọi caller dùng: nó trả về config đã đổi `host`/`port` sang cổng đã forward, kèm handle của tunnel. **Thả handle là đóng cổng**, nên ai sở hữu kết nối cũng phải sở hữu tunnel — `ServerHandle.ssh_tunnel`, dùng chung cho SQL lẫn Redis.
- `redis_db/` — transport config (the rest of the file is the Redis browser itself):
  - **TLS is a mode, not a switch.** `redis_ssl_mode()` folds the UI's `sslEnabled` + `sslMode` into DISABLED / REQUIRED / VERIFY_CA / VERIFY_IDENTITY. An *absent* mode with the switch on means VERIFY_IDENTITY, because that is what the old switch-only profiles actually did (`rediss://` verifies fully under rustls) — mapping them to the weakest mode would silently downgrade every saved connection. PREFERRED is not offered (Redis has no STARTTLS negotiation) and is mapped up, not down. Its twin on the frontend is `REDIS_SSL_MODES` in `ConnectionManager.tsx`.
  - REQUIRED is the `#insecure` URL fragment and VERIFY_CA is `set_danger_accept_invalid_hostnames`; **both need the `tls-rustls-insecure` feature** on the `redis` crate or the connection fails at handshake time with a config error. The hostname flag must be applied **after** `Client::build_with_tls()` — that call rebuilds `tls_params` from the certificate files and would drop a flag set before it.
  - CA / client cert / client key come from the same `sslCaPath`/`sslCertPath`/`sslKeyPath` fields as Postgres and MySQL, but redis-rs wants **file contents**, not paths, so they are read into `TlsCertificates` (a half-set mTLS pair is rejected in the form's own words rather than left to fail as an opaque TLS error).
  - **A Redis `ServerHandle` keeps the TUNNELED config** — unlike SQL, which keeps the original and reopens a tunnel every time it builds a pool. Redis reconnects far more often (db-index switch, Pub/Sub, Profiler each open a new socket) and the tunnel is already alive on that very handle, so `select_db_inner` and `dedicated_client` reconnect through it instead of opening a second one. Consequence worth knowing: over a tunnel the certificate is presented for `127.0.0.1`, so VERIFY_IDENTITY cannot work and the SSL tab says so.
  - **Xuất / nhập keyspace theo prefix** (`redis_dump_keys` / `redis_restore_keys`, driven by `RedisTransferDialog.tsx`, file format in `utils/redisTransfer.ts`). The decisions worth knowing:
    - **DUMP/RESTORE, not a readable JSON serializer.** Both existing read paths are lossy: `fetch_elements` puts every element through `lossy_text` (non-UTF-8 bytes become U+FFFD — that is what the `binary` flag locks editing for) and `redis_get_key` truncates strings at `STRING_PREVIEW_MAX`. An export built on those corrupts data silently, which is the worst possible failure for a backup feature. A DUMP payload is Redis's own bytes: exact, and it covers the types the app has no editor for (ReJSON, TimeSeries, vector set). The cost, stated in the dialog: the payload carries an RDB version footer, so it only restores into a Redis of the same version **or newer**.
    - **Reads are pipelined, writes are not.** `DUMP` of a missing key returns Nil rather than an error, so a whole batch can never be broken by one key. `RESTORE` can (BUSYKEY), and a pipeline reports only the *first* error while the server still executes the rest — so re-running the batch to attribute errors would hit BUSYKEY for keys it had just created and report them as "already existed". `redis_restore_keys` therefore runs key by key; the frontend batches at 200 so progress still moves.
    - `payload` travels as **base64**, not as the byte array `redis_get_key` uses for `bytes` (~3× smaller over IPC, and it is what goes into the text file). `base64` is a direct dependency for this, already in `Cargo.lock` beforehand.
    - BUSYKEY is counted as **skipped**, not failed — an ordinary import into a db that already holds some of the keys would otherwise look like thousands of errors. `failed[].error` is Redis's own English text and deliberately does **not** go through `backendErrors.ts`.

### Frontend (`src/`)

- `App.tsx` — top-level state owner: active connection, the tab list (`TabInfo[]`, each tab is either a `table` or a `query`), theme, and all the global Import/Export/Backup-Restore modals (these are large inline JSX blocks rather than separate components — follow that pattern if extending them, or consider extracting if they grow further). Cross-component signals that don't fit the props tree use `window` `CustomEvent`s: `table-renamed` and `database-restored` (dispatched after imports/restores so `Sidebar`/`DataGrid` can refetch).
  - **The SQL dump is built in `utils/dumpBuilder.ts`** (`buildDump`), called both by `handleExportDatabase` here and by Connection Manager's Backup button — the Rust `export_multi_tables` it replaced treated views as tables, wrote one `INSERT` per row and had no routines, so every fix made for the dialog missed the Backup path. DB access is injected as a `reader` param (`dbHelper` matches the shape) so the module imports no `@tauri-apps/api` and the statement order is unit-tested (`dumpBuilder.test.ts`). That **order is load-bearing**: sequences → base table (DDL, indexes, comments) → data → deferred FK/UNIQUE/CHECK (`ALTER TABLE ADD CONSTRAINT`, only after *every* table exists) → `setval()` (reads `MAX()` of the rows just inserted) → views → routines → triggers. `get_table_ddl_extras` supplies the per-table extras: nothing for MySQL (`SHOW CREATE TABLE` has it all), indexes for SQLite, and index/FK/CHECK/comment/sequence for Postgres, whose `CREATE TABLE` is hand-built from columns + PK only. Routines and triggers come last because their bodies read tables and a trigger may call a function; on MySQL they are wrapped in one `DELIMITER $$` block (`wrapMysqlDelimiter`), and every DDL goes through `stripDefiner()` — a kept `DEFINER=user@host` makes the restore fail with error 1227 for anyone else. Data fidelity lives here too: `generated`/identity columns are dropped from the INSERT column list (MySQL 3105) and binary columns are written as `X'..'` / `'\x..'::bytea` via `isBinaryType()`, because the backend ships a BLOB as a byte **array** that would otherwise be stringified into `'[137,80,...]'`. Triggers follow their table in `ExportDatabaseDialog` (ticking a table ticks its triggers, like `mysqldump`); the dialog groups the list by kind because 23 sakila tables pushed routines below the fold and they looked missing. Older text, still true of the table/view part: every base table (DDL + data) first, then every view. `CREATE VIEW` is validated when it runs, so a view emitted in the sidebar's alphabetical order landed before the tables it selects from and the re-import died on MySQL 1146 — `actor_info` is the second name in sakila. Views carry `DROP VIEW`/`CREATE VIEW` (never `DROP TABLE`, which cannot drop a view) and **no data** (`INSERT` into a non-updatable view fails, and the rows are already in the base tables). Between views the order comes from `orderViewsByDependency()` in `exportHelper.ts` — a view may read another view. `ExportDatabaseDialog` therefore passes `views: string[]` alongside `tables`; `dbHelper.getTables()` is where the table/view distinction comes from.
  - **A dump written to a folder is streamed**: `writeDump(spec, reader, emit)` emits it a table and a PAGE of rows at a time, every chunk ending between two statements, into `fileSave.ts`'s `saveDumpToFolder` → Rust `export_sink.rs` (`.part` file renamed on close, gzip via `flate2`). `buildDump` is `writeDump` collected into one string, byte-identical to before — the tests use it and the copy-database path needs the whole string for `restore_backup`. Add a new section to the dump through `parts` + `flush()`, never by returning text, or it lands out of order.
  - `buildSql()` batches rows into multi-row `INSERT`s (500 rows / 200k chars per statement). One INSERT per row made a sakila dump ~50,000 statements, and `restore_backup` runs each one as its own round trip. Its reader twin is `parseInsert()` in `dumpPreview.ts` — that one walks tuples by index, not by re-slicing the remainder, because these statements are now hundreds of KB (`exportHelper.test.ts` pins the round trip).
  - Table/view names are detected from a dump in exactly one place: `parseDumpTableNames()` / `dumpStatementObject()` in `dumpPreview.ts`. There used to be four copies of that regex (both dialogs, the count memo, and a Rust `parse_backup_tables` command — since deleted, it had no caller left and its stale regex would have silently dropped views/routines/triggers for whoever called it next), and none of them matched `CREATE VIEW`/`DROP VIEW` — a view then never reached the selected-tables list, so `stmt_mentions_table` on the Rust side silently dropped its statements.
  - Both restore dialogs (`ImportDatabaseDialog`, `ConnectionManager`'s Backup/Restore) split the dump **once per file** into a precomputed array (`table`/`kind`/`skipped`/`commentOnly`). The count and the previews only read that array. Do not add a `useMemo` over `sqlText` keyed on the selection — that is what made every checkbox tick re-scan 10M characters.
- `utils/dbHelper.ts` — the only place that calls `invoke()`. Defines the shared TypeScript types (`DbConnectionConfig`, `TableItem`, `ColumnInfo`, `SchemaInfo`, `GridChange`) that describe the JSON contract with `database/`. When the Rust side's JSON shape changes, update the corresponding method here.
- **Per-connection localStorage: always scope through `utils/connKey.ts`.** Never key user state by `dbName` alone — it is `config.database || config.sqlitePath` (`dbHelper.connect`), so two servers hosting a database of the same name shared one key, and every Redis server collapsed into `db0`. `connKey(config)` identifies the **server** (`mysql:host:port`, or the normalized SQLite path; credentials excluded, SSH-tunnel rewriting happens in Rust so the real host is used), `scopeKey(config, db, schema)` identifies server + database + Postgres schema. Tabs (and the SQL auto-saved inside them) use `scopeKey` via `tabsStorageKey()`, because a tab list belongs to one database and — on Postgres — to one schema of it. **The key gained levels over time, so writing and reading are asymmetric**: only the newest spelling is ever written, while `tabsStorageKeyCandidates()` reads the newest, then the schema-less key, then `legacyTabsStorageKey()`, so an upgrading user's workspace is carried forward instead of vanishing. The `:schema` suffix is appended **only when the schema is not `public`**, which is what keeps every pre-schema key spelled identically. Query history is stored as one list and *filtered* at display time (see below). That write is the biggest thing in localStorage (draft SQL × tabs × databases), so it is wrapped in a try/catch that retries without the inactive tabs' drafts on `QuotaExceededError`.
- `utils/queryHistory.ts` — the store behind the SQL editor's history drawer (`sql_query_history` / `sql_saved_queries`). Every mutation is a read-modify-write against localStorage, **never a write of component state**: each query tab mounts its own `SqlEditor` holding its own copy, so writing state back resurrected entries another tab deleted. After each write it dispatches `sql-history-changed` so the other mounted editors reload. Entries carry `conn` (a `connKey`) + `db`, and the drawer filters them through `matchesScope()` with three scopes — `db` (default), `conn` (every database of that server, so a `USE` timeline stays whole), `all` — persisted in `tf_history_scope`. Both fields are optional and an entry without them matches **every** scope, which is how pre-existing history survives; that is also why `clearHistory()` deletes untagged entries only at scope `all` (deleting them from one scope would silently delete them from the others). The 500-entry cap is applied **per `conn`** (`trimHistory`) so a busy connection cannot evict the others. A row is written when the run *starts* (`addHistoryEntry` returns its id) and the outcome is patched on when it finishes (`recordHistoryResult`: `ok`/`ms`/`rows`/`affected`/`error`, the error truncated to `ERROR_MAX_LENGTH`) — `ok` stays **undefined** for a run the user stopped and for every row written before this existed, so the drawer shows no status icon rather than a wrong one. Re-running the statement at the top of a connection's history reuses that row (moved back to the top, result cleared) instead of adding a duplicate, which is why the array order can be relied on as newest-first.
- `utils/redisTransfer.ts` — the file format behind Redis **export/import of a keyspace by prefix**, built on the same pipeline as `dumpBuilder.ts`: the content is assembled here and DB access is injected (`RedisExportReader` / `RedisImportWriter`, which `dbHelper.redisScanKeys`/`redisDumpKeys`/`redisRestoreKeys` match), so the module imports no `@tauri-apps/api` and the format is unit-tested (`__tests__/redisTransfer.test.ts`). Format is **NDJSON**: a header line, one line per key (`{key,type,ttlMs,payload}` — the *same* field names `redis_dump_keys` returns and `redis_restore_keys` accepts, so nothing is renamed between Redis, the file and Redis again), then a footer line carrying the count. Three things are load-bearing. (1) **The footer is only written for a complete export** — hitting `EXPORT_KEY_CAP` or being stopped deliberately leaves it out, and `parseRedisExport` reports that as `truncated`, which is the only way an incomplete file can be told from a whole one. (2) **A bad line does not fail the file**: it goes into `badLines` and the rest still imports, because "the whole 100k-key file is void because line 4 is broken" is the worst outcome available. (3) `prefixPattern()` escapes glob metacharacters by delegating to `folderMatchPattern()` rather than carrying its own copy — without escaping, prefix `log[1]:` scans for keys starting with `log1:`, i.e. exports the wrong set with no error; `patternToPrefix()` is the reverse (the key browser's search box holds a *pattern*, the dialog takes a *prefix*) and returns `''` rather than guess when the body still holds glob syntax, since `prefixPattern` would then escape it a second time. Entry points: the key-list header's ⇅ button (current search pattern) and a key-tree folder's context menu (a real prefix, so no guessing). Adding a `redis_*` command means classifying it in `utils/safeMode.ts` too — `safeMode.test.ts` reads `dbHelper.ts` and fails on an unclassified one.
- `utils/jobs.ts` + `components/JobsTray.tsx` — **việc chạy nền**: Export Database, Import/Restore, Backup/Restore của Connection Manager và Data Generator không còn giữ cả app lại chờ. Ba điều load-bearing. (1) Store nằm **ngoài React** (khuôn `queryHistory.ts`/`safeMode.ts`): job phải sống lâu hơn mọi dialog — mà dialog bị unmount theo thiết kế — và nếu tiến độ nằm trong state của `App` thì mỗi tin tiến độ re-render **mọi tab**, đúng thứ mà debounce 150ms của `SqlEditor` sinh ra để tránh. (2) Bản ghi job là **immutable**: sửa tại chỗ thì `useSyncExternalStore` thấy cùng một tham chiếu và tray đứng im. (3) Một database đang bị GHI là **độc quyền** — hai restore vào cùng một database không bao giờ là ý người dùng, và xuất dump trong lúc restore đang ghi lại thì được một tệp bị xé, nên job ĐỌC cũng phải chờ job GHI trên cùng `lockKey`; hai job ĐỌC thì chạy song song, cap 3. Mọi chuỗi (`title`, `result.message`, nhãn tiến độ) truyền vào **đã dịch sẵn** — module này không có `t()`, cùng luật với `SafeModeRequest.detail`. Ba lệnh dài (`restoreBackup`, `generateData`, `cancelDataGeneration`) và `getAllTriggers`/`getTableDdlExtras` vì thế nhận `connId` **tường minh**: một job có thể nằm trong hàng đợi, và tới lượt nó thì `currentConnId` (ambient) đã là kết nối khác, tức là restore vào đúng database người dùng không chọn. Nút trên thanh tiêu đề là một cái **chuông** mở popover neo ngay dưới nó (`.jobs-pop` dùng CHUNG rule với `.sm-pop` của Safe Mode bằng một selector ghép trong `index.css`, không phải bản sao — dáng popover của thanh tiêu đề sửa một chỗ là cả hai đổi), không phải hộp thoại giữa màn hình — xem một việc đang chạy nền không được che thứ người dùng đang làm. Kế hoạch và phần chưa làm: `docs/background-jobs-plan.md`.
  - **Mỗi job chạy trên một `conn_id` của riêng nó** — `utils/jobConnection.ts` (`withJobConnection` / `runOnJobConnection`) là đường duy nhất, và job mới phải đi qua nó. Session transaction thủ công, cờ huỷ (`cancel_flags`) và guard `reject_if_manual_or_open` đều khoá theo `conn_id`, nên một job chạy trên id của người dùng là job nhập vào transaction của họ. Backend: `open_job_connection` mint id mới **dùng chung pool** của nguồn (không xác thực lại; SQLite thì mở handle thứ hai với `busy_timeout`), entry mang `ConnPurpose::Job` nên `list()`/`find()`/`find_sqlite()` không bao giờ trả nó ra; `connect_db(job: true)` là bản cho Connection Manager (mở từ form, không đổi ambient id). Safe Mode hỏi **lúc submit** (`approveJob`/`approveJobForServer`) rồi `openJobDoor` mở cửa cho đúng lệnh đó trên đúng id của job — không bao giờ hỏi giữa lúc chạy nền.
  - `utils/jobHistory.ts` giữ kết quả của 50 job gần nhất qua các lần mở app (`tf_job_history`), ghi từ `settle()` của `jobs.ts`; job huỷ khi còn trong hàng đợi không được ghi.
  - `utils/jobNotify.ts` — thông báo của HĐH qua lệnh `notify_os` (`app/notify.rs`, dùng thẳng `notify-rust`) khi một job xong hoặc lỗi **lúc cửa sổ không được focus**; huỷ thì không báo. Nghe qua `onJobSettled` của `jobs.ts`, đăng ký trong `JobsTray` (luôn được mount), có công tắc + nút "Gửi thử" ở cuối popover. **Không dùng `tauri-plugin-notification`**: plugin chọn AppUserModelID của Windows theo đường dẫn exe (chỉ `…\target\debug|release` mới là dev), mà `CARGO_TARGET_DIR` của repo này là `C:\cargo-targets\tablegrid`, nên bản dev dùng ID `com.tablegrid.desktop` chưa đăng ký và Windows lặng lẽ bỏ mọi thông báo. `notify_os` quyết định theo `tauri::is_dev()` và trả lỗi về.
- `utils/localHistory.ts` + `localHistoryPolicy.ts` + `components/LocalHistoryDialog.tsx` — **local history** of each query pane (FileClock button, or F1 / context menu → "Local history…"). A query tab is a localStorage draft, not a file, so before this there was no way back from pasting over a statement, pressing Clear, or closing the tab; query history only keeps what was RUN. Five things are load-bearing:
  - **IndexedDB, not localStorage.** The drafts are already the biggest thing in localStorage (see the `QuotaExceededError` retry above), and sixty snapshots per pane would push them out. Every store call swallows its errors — a missing IndexedDB means no history, never a broken editor.
  - **When** is decided in the pure, tested policy: on Run (the whole pane), on the existing 600ms sync flush but at most every 2 minutes, before Clear/Paste/Restore, and — the case the throttle would miss — the text BEFORE a large deletion (`isBigDeletion`, compared against the previous flush). Prune: 60 per pane, 30 days, a 12M-char total budget; a pane over 1M chars is a pasted dump and is not snapshotted.
  - **Keyed by scope (`connKey|dbName`) + tab id + pane**, not by an open tab, which is what makes a CLOSED tab recoverable: the dialog's "All tabs on this database" lists snapshots whose tab no longer exists, and the unmount cleanup writes a final `close` snapshot for exactly that reason.
  - **Paste and Clear used `editor.setValue()`, which wipes Monaco's undo stack**; they now go through `replacePaneText` (snapshot, then one `executeEdits` between undo stops), the same path Restore uses, so Ctrl+Z undoes all three.
  - The dialog renders Monaco's `DiffEditor` and is imported **only** by `SqlEditor`, which is what keeps it inside the lazy chunk (see the Monaco build notes) — do not import it from anything the entry reaches.
- `utils/closeGuard.ts` — **một** listener `onCloseRequested` cho cả app; ai muốn chặn thì `registerCloseBlocker(priority, fn)`, trả `true` nghĩa là "tôi chặn và đã tự hỏi người dùng". Hai listener độc lập KHÔNG dùng được: mỗi cái đều `preventDefault()` rồi một cái gọi `destroy()`, nên cái nào resolve trước cũng giết luôn hộp thoại của cái kia — đó là lý do `TxControl` chuyển guard "còn thay đổi chưa commit" của nó thành một blocker. Ưu tiên theo mức thiệt hại chứ không theo thứ tự mount: transaction chưa commit (không lấy lại được) trước job đang chạy. Blocker ném lỗi thì coi như không chặn, vì một guard hỏng không được phép giữ người dùng trong một app họ không đóng được.
- `utils/safeMode.ts` — **an action that runs several backend commands must go through `runApproved()`, not through the per-call gate.** `approveCommand()` sits in front of every `invoke()` (`dbHelper`'s single local funnel), which is correct as long as one user action is one command — true of `commit_changes`, `restore_backup`, `generate_data` and every other write until the Redis keyspace import, which calls `redis_restore_keys` once per batch of 200 and therefore asked 50 times for 10,000 keys. Nobody answers 50 dialogs; they switch Safe Mode off, so the cost of the feature becomes the loss of the guard. `runApproved(cmd, connId, detail, run)` asks **once** and holds a door open for the duration: keyed on the exact command *and* connId (an approved import cannot carry a `redis_flush_db`, or the same command on another connection, through with it), closed in a `finally` so a run that throws does not leave it open, and depth-counted so a nested or concurrent run ending does not close the outer one's door. It deliberately does **not** remember the answer afterwards — there is no "don't ask again". The `detail` string is passed in already translated (`SafeModeRequest.detail`, rendered above the command name by `SafeModeGate`) because a once-per-run question has to say *what* it is approving — "import 10,000 keys, overwriting existing" — and this module has no `t()`.
- `utils/vault.ts` + `components/{LockScreen,MasterPasswordModal}.tsx` — **Master Password**, phía frontend. Store nằm **ngoài React** (khuôn `jobs.ts`/`queryHistory.ts`): trạng thái khoá được hỏi bởi những component không phải tổ tiên của nhau (overlay ở root, dialog cài đặt bên trong Connection Manager, nhánh lỗi trong `persistProfiles`), mà nâng nó lên `App` thì mỗi lần đổi là re-render mọi tab. Ba điều chịu lực:
  - **`LockScreen` là OVERLAY, không phải early return.** `App` giữ mọi query tab được mount để kết quả một lần chạy sống qua lượt đổi tab; khoá do rảnh mà unmount cả cây là vứt bỏ nội dung editor, kết quả, vị trí cuộn — để bảo vệ những bí mật mà backend đã niêm phong xong rồi. Nó tự mang thanh kéo cửa sổ + ba nút min/max/close, vì nó che mất title bar thật, và một app không di chuyển/đóng được thì không phải "đã khoá" mà là "bị kẹt".
  - **Khoá KHÔNG đụng tới kết nối đang mở.** Ngắt kết nối sẽ huỷ phần việc chưa commit của một transaction thủ công (`tx/`) và giết job đang chạy của `jobs.ts` — mất dữ liệu người dùng nhân danh việc bảo vệ họ. Cái mà khoá chặn là ĐỌC BÍ MẬT, không phải phiên làm việc đang có.
  - **Trạng thái khoá được HỎI, không được đọc từ chữ.** Lỗi backend đã bị dịch ngay ở biên `dbHelper`, nên so khớp văn bản "kho đang khoá" sẽ hỏng ngay lần đổi ngôn ngữ đầu tiên — đúng luật "không rẽ nhánh theo chuỗi hiển thị". Mọi nhánh catch quanh secret (`connectProfile.configWithSecrets`, `configWithSecrets`/`persistProfiles` của Connection Manager) vì thế gọi `refreshVaultStatus()`, và chính câu trả lời của backend dựng lại lock screen.
- `components/`:
  - **Buttons are `className="btn btn-secondary"` / `"btn btn-primary"` — both classes.** `.btn` alone carries the geometry (28px height, 8px radius, 11.5px/600); `btn-secondary` on its own only sets colours, so the button renders at the browser's default size and squared corners. Same trap for inputs: the shared style matches `input[type="text"]`, so an `<input>` written without a `type` gets no background or border at all.
  - **Inline `style={{…}}` is for values computed at runtime; anything static belongs in `index.css`.** The line is real but eroding — 1982 inline `style` props against 2934 `className`s, and the gap only closes when someone moves a batch (the sixteen constants `Sidebar.tsx` used to carry were one such batch). Two halves to the rule. (1) **Never write a bare colour, font or radius inline.** The app swaps themes through `[data-theme='dark']`/`[data-theme='light']` over 29 `--win-*` tokens, so a hardcoded `#0284c7` is correct in at most one of the two themes; the 182 such literals still in the tree (73 of them in `WhatsNewModal.tsx`) are a backlog, not a precedent. Use `var(--win-…)`, and a hex **only** as its fallback (`var(--win-danger, #ef4444)`, 51 uses). (2) Inline is the right answer for a value the render computes — a measured width, a `transform` from drag state, a per-row colour from data — and the wrong one for `display: flex; gap: 6px`, which is a class by the third time you type it; a static object literal is also rebuilt every render, so it defeats memoization in any child that receives it as a prop.

    - **`content-visibility: auto` on `.sidebar-row`** is the lazy renderer: the browser skips style, layout and paint for any row not near the viewport.       - **Where the rows come from.** `DataGrid` pages *and* sorts on the SERVER (`getTableData` with `LIMIT`/`ORDER BY` plus keyset cursors); the result grid holds the whole result in memory and pages and sorts on the client (`sortedResults1/2`).

Picking only among the connections already open was the first shape and it made the ordinary case impossible: with one connection open there was nothing to copy INTO, and `sakila` → `sakila_backup` on one server needed the target opened by hand first. - `components/er/` — the ER diagram: a pan/zoom **canvas** (one `<canvas>`, no DOM per table), driven by `ERDiagramTab` (Sidebar → ER Diagram). Two Figma-style tools, `select` and `hand` (`V`/`H`, Space borrows `hand` from either, middle-drag pans in both, `Shift`+`0`/`1`/`2` reset/fit/zoom-to-selection). `erViewport.ts` holds every bit of the math as pure functions **because a bug in it shows up as content in the wrong place, and there is no element inspector to find it with** — `erViewport.test.ts` pins the cursor-anchored zoom, the LOD thresholds and the culling rectangle; `erScene.test.ts` pins hit testing, the raster scale and the bitmap cache key.
  - **It was HTML cards over an SVG connector layer, and the rewrite is the whole story of this directory.** A profile at 320 tables / 537 FKs (`scripts/make-er-mock-db.mjs` writes such a database) put 340ms of 6,463ms of main-thread time in app code — **almost none of the cost was JavaScript**, so every React-side lever had already been pulled and what was left was style, layout and paint for ~10 elements per column row. The hard ceiling was zoom: a composited layer re-rasterizes its whole content whenever the transform SCALE changes, so a wheel gesture repainted 2.25 screens of DOM every frame. It arrived as a field report — "above 70% zoom it lags, below 70% it is fine" — 0.7 being exactly `LOD_NAMES_BELOW`, where the `full` level starts. A canvas removes style and layout entirely and turns paint into blits.
  - **A card is rendered ONCE into an offscreen bitmap and blitted after that** (`erCardRenderer.ts`). Everything else follows from that sentence:
    - **The raster scale is not the zoom.** `quantizeRasterScale` snaps it to ~√2 steps and it is re-evaluated only when a gesture SETTLES, so a wheel burst re-uses the bitmaps it has and the cards go slightly soft for a moment rather than every visible card re-rendering per frame. This is the trade a map renderer makes with tiles, and it is the single decision that makes zooming cheap — do not make it follow the live zoom.
    - **The cache is capped in BYTES, not entries** (64MB, LRU). A card at raster scale 2 is ~400KB, so a few hundred of them is half a gigabyte; an entry count cannot express that, and the cards it would keep are the cheap ones.
    - **`blocks` is deliberately NOT cached, and it has its own draw function** (`drawBlockCard`, not `drawCard` with the body skipped). At that zoom a card is a filled rectangle, cheaper to draw than to look up, and it is the one level where fit-to-view puts thousands on screen at once — where a bitmap per card would be a memory disaster rather than a saving. It is also the level where anything invisible is invisible **two and a half thousand times**: sharing `drawCard` meant a `save`/`clip`/`restore` to paint the header band and a `measureText` + ellipsis fit + `fillText` for a title 0.36px tall, per card, per frame — measured at **23ms average / 43ms worst** on a 2514-card, 4499-connector frame. `blockCardDetail(zoom)` gates both by legibility: the corner radius below ~1.5 device pixels, the title below ~5px. Two fills, and a `fillRect` rather than a ten-segment path when the rounding cannot be seen.
    - **A frame may render at most `CARD_FILL_BUDGET` new bitmaps**, draws the rest as skeletons and reports itself incomplete so the caller draws again. Without it, one frame can be asked to render every card it can see — fit-to-view, a theme switch, a detail-level change — which is the stall this renderer exists to remove.
    - A theme switch invalidates the cache through `ERPalette.id` (keyed on `data-theme`), so there is no explicit invalidation to forget; the cache is *also* cleared outright, because stale bitmaps still hold their bytes. Web fonts are the one change no attribute describes — until `document.fonts.ready`, `fillText` bakes the fallback family into a bitmap for the life of the tab, hence `invalidateErPalette()`.
  - **`erTheme.ts` is the only place the canvas learns a colour.** `getComputedStyle` flushes style, so it runs once per theme and never inside a frame or a card render. Changing a `--win-*` token still changes the diagram; adding a CSS rule for a card does nothing, because there is no element for it to match.
  - **A gesture never renders, and now neither does a pan.** `viewportRef` is the only viewport — the committed snapshot, `needsRecommit()` and `CULL_MARGIN` went with the mounted set they existed to stabilize. Pointer, wheel and tween handlers write the ref and ask for a frame; `flush()` runs a queued frame when the pointer comes up, so what gets saved is the position on screen and not the previous frame's. A node drag writes `positionsRef` directly each frame and tells React once, on release — and the sync effect **must not** overwrite `positionsRef` while that drag is in flight (`gestureRef.current?.kind !== 'node'`), or a render landing mid-drag puts the pre-drag positions back under the pointer.
  - **Hit testing is geometry, not the DOM.** `hitTestCards` walks the positions in REVERSE draw order, because the topmost card is the one drawn last. `hitTestRelationships` flattens each curve into 14 segments and **must** be culled to the screen first: resolving a connector's sockets calls `getColumnSocketPosition`, which scans the table's columns by name, so uncelled it is O(relationships × columns) on every pointer move — six figures of string comparisons per mouse movement at 5000 FKs. `document.elementFromPoint` is gone, and with it the forced layout it caused.

Which of the two honest tests to use depends on the zoom, and the canvas rewrite got this wrong once: `connectorHasVisibleEnd` was deleted on the argument that a connector is now just a few segments in a batched `Path2D`, and `__erPerfDebug` then showed **176 connectors drawn against 7 visible cards at zoom 1.00** — ~140 dashed lines crossing the view with both ends, both sockets and the arrow head off screen, each still costing two socket resolutions, a curve, two arcs and an arrow head. So: endpoint test at `full`/`names`, where such a line says nothing; segment test at `blocks`, where those diagonals ARE the shape of the graph and a connector is two points. `connectorIntersects` is conservative by construction (the curve stays inside the centre-to-centre segment grown by half a card plus the bezier reach), so nothing visible is ever culled.
  - **At `blocks` a connector is a straight `lineTo`, not a bezier** — which is what the old flattened SVG path drew too. The bow is at most 180 world units, under a device pixel down there, and skipping it saves both the control-point object and the curve flattening the rasterizer does per path, 4499 times in the fit-to-view frame.
  - **Connectors are drawn as SIX batched paths, not four draws per connector** — curves, sockets and arrow heads, each split plain/lit — so the whole layer is a fixed handful of submissions however many foreign keys are on screen. A canvas path costs what it costs to submit far more than what it holds, and at `full` a couple of hundred visible connectors had been ~750 `beginPath`/`fill`/`stroke` calls per frame. The dash pattern is the other reason to batch: dashing makes the rasterizer flatten every curve and lay out every dash along it. Sockets and arrow heads exist **only** at `full`, where both are still over a device pixel. The lit batch strokes at `2.5 / zoom` so it stays readable at any zoom, which is what `vector-effect: non-scaling-stroke` used to do.

Hover is what makes this matter: with no retained scene, moving the pointer across a card boundary repaints everything, so the frame cost IS the pointer's responsiveness.

All numbers are from `scripts/make-er-mock-db.mjs`-shaped schemas (~79% of foreign keys inside a module), reading the median connector length and how many connectors a centred viewport mounts at 85% zoom:
    - *Layering alone*, which is what it did originally: it ran step one of Sugiyama and then placed each layer in whatever order a `Set` iterated in, so two tables sharing a parent could sit at opposite ends of a column. It also had a `nextLayerSet.size < 6` escape hatch that let a table into a layer before its parents, which did not merely tolerate FK cycles but **created** long backwards edges in schemas that had none. `breakCycles` (DFS back-edge removal) replaced it.
    - *Adding barycentric ordering across the whole diagram* — the textbook fix, and it under-delivered: median −12%, mean −5%. The reason is the **column height budget**: keeping a few hundred tables screen-shaped forces each layer to wrap into several columns, and once a layer wraps, a table's index within it is no longer its y coordinate — which is the one assumption barycentric ordering rests on. The wrap was quietly cancelling the ordering.
    - *One block per module, layered inside it*, which is what ships: median **−7% at 320 tables and −37% at 1200**, connectors mounted at 85% zoom **−53% and −31%**. A module is small enough to need little or no wrap, so inside a block the ordering means what it says. What is given up is that the left-to-right FK reading is now per module rather than diagram-wide — which is where it was being read anyway, since nobody traces a foreign key across thirty columns.
    - Finding the blocks was **not** community detection. Label propagation is the textbook answer and it collapses: labels update in place in a fixed order and ties go to the smaller one, so the alphabetically smallest label sweeps the graph — it returned ONE community of 1200 on a schema with 79% intra-module edges, and a seeded shuffle only makes it unstable rather than correct. Layout does not need true communities, it needs a partition into workable blocks with most edges internal, and stated that way `partitionIntoBlocks` is greedy size-capped growth: busiest table left, then whichever neighbour has the most edges into the block. **Fill every block to the cap even after its frontier runs dry** — ending it there fragmented 320 tables into 70 blocks of four instead of 12 of 27, which inflated the diagram by the gaps, lengthened the mean connector, and made `orderBlocks` quadratic over hundreds of entries (183ms at 2500 tables, now 32ms).
    - `TARGET_ASPECT` for the shelf packing is 2.2, above a screen's own 1.78 because ragged rows come out squarer than asked. At 1.5 the packing was handing back the entire screen-shape win: fit-to-view zoom 0.081 against 0.122.
    - The column budget itself still applies, now per block: solving `columns * pitch = stack / columns` keeps a block from being a ribbon, and the 1200px floor leaves a small diagram laid out one layer per column exactly as before. Tables with **no** foreign key are packed into a grid of their own after the flow — sharing layer 0 with the real root tables, they used to stretch its first column for no reason.

## Project overview

TableGrid is a desktop database GUI client (Tauri 2 + React 19) similar in spirit to DBeaver/TablePlus. It connects to SQLite, PostgreSQL, and MySQL, and lets the user browse/edit table data, alter schemas, run raw SQL, and backup/restore databases. The window uses a custom title bar (`decorations: false` in `src-tauri/tauri.conf.json`) with its own drag/min/max/close controls in `TitleBar.tsx`.

Many user-facing strings, backend error messages, and Rust comments are written in Vietnamese — preserve this convention when touching existing strings/comments.

## Commands

Development requires a native toolchain on Windows: Rust (cargo), a MinGW64 GCC toolchain on PATH (for linking), and Node.js.

  - `oxc/no-map-spread` is `"off"`, and this one is the important off-switch: all ten of its findings were **immutable updates** — `map(c => cond ? { ...c, ...patch } : c)`, defensive copies into React state, derived arrays. Its advice (`Object.assign` in place, or direct property assignment) would mutate state that is still shared, which is the classic "state changed but React did not re-render", and in `aiSessions.ts`/`connectionProfiles.ts` would mutate an object the caller still holds. Following this rule here produces bugs.
  - **`eslint-disable-next-line react-hooks/exhaustive-deps` DOES suppress oxlint's `react/exhaustive-effect-dependencies`** — verified, so the existing documented disables are not silently dead. That backlog is now at **zero**: every site is either a dep that was added or an omission carrying a comment saying why. Keep it there — guessing between the two causes a render loop, so a new finding is worth reading rather than suppressing.
  - `no-shadow` earns its place and is now at **zero**: 33 of its original 43 findings were `t` shadowed by a `.map(t => …)` callback in a file that also calls the translation `t` — the exact hazard the i18n notes below describe. One more was worth the rename on its own (`Sidebar`'s `const schema = await getTableSchema(…)` shadowed the *Postgres schema* named `schema`). Rename the callback rather than disabling; twice during that cleanup the replacement name collided with an existing binding and `tsc` caught it, so check the build rather than trusting the rename.
  - **The two big standing groups are triaged, not ignored — don't re-derive this.** `react/no-array-index-key` (~49) and `eslint/no-await-in-loop` (~40) are left as warnings on purpose, because in this codebase the finding is usually *correct behaviour*:
    - **index keys**: the result grids (`SqlEditor`, `DataGrid`, `DataGeneratorDialog`, import previews) key `<th>`/`<td>` by position **because CLAUDE.md requires it** — duplicate column names collapse otherwise. Append-only logs (redis Console/Profiler/PubSub, `TerminalPanel`, statement lists) and `StructureViewer`'s DDL block (which renders `idx + 1` as the line number) have the index *as* the identity. What is left is the row editors (`CreateTableModal` ×3, `ViewEditorModal`, `CreateRoutineModal`), where deleting a middle row can land focus on the wrong input. Fixing those needs a stable id **added to the state shape** — `key={col.name || idx}` is worse, because clicking "add column" twice gives two rows with an empty name and therefore duplicate keys. Not worth the refactor for a focus glitch; if you do it, add the id.
    - **`await` in a loop**: every site is a sequential DB read — paging (`getTableData(table, page, …)` in `dumpBuilder`, `ExportTableDialog`) or one query per table (`schemaSnapshot`). `Promise.all` there would fire N concurrent queries at the user's production database, which this app avoids on purpose. The rule cannot tell that apart from a slow loop over local data. The same goes for the streamed dump's writes (`writeDump` awaiting its `emit`): chunks must reach the file in order, and awaiting each one is what stops unwritten pages piling up in memory.

## Architecture

### Process split

- **Frontend** (`src/`): React 19 + TypeScript, built with Vite. All UI, state, and SQL/CSV parsing logic lives here. No direct DB drivers — every DB operation goes through Tauri's `invoke()`.
- **Backend** (`src-tauri/src/`): Rust, exposes `#[tauri::command]` functions as the only bridge to the frontend. Holds the actual DB connections and does all SQL execution, schema introspection, and file I/O (export/backup/restore).

The frontend never talks to a database directly — `src/utils/dbHelper.ts` is the single wrapper around every `invoke()` call and is the de facto contract between the two sides. When adding a new backend capability, add the `#[tauri::command]` in the right `database/commands/*.rs`, register it in the `generate_handler!` list in `app/handlers.rs`, then add a corresponding method to `dbHelper`.

**Every `#[tauri::command] async fn` obeys two rules, and breaking either one crashes the RELEASE build at the first call while `tauri dev` stays perfectly happy.** All 143 of them follow both; a new one must too.

1. **Never take `tauri::State<'_, AppState>`.** Read the state with `crate::state::require_state()?` instead. That parameter carries a lifetime, so the command's future is not `'static`; Tauri can only `spawn` a `'static` future onto the async runtime, and anything else it builds *and runs* on the calling thread — the main thread, whose stack Windows reserves at **1MB** (Linux and macOS give 8MB, which is why this is invisible on those). `AppState` is `Clone` over an `Arc`, so `require_state()` costs one refcount bump.
2. **Wrap the body in `Box::pin(async move { … }).await`.** `#[tauri::command]` expands to `async move { let result = $path(args); … kind.future(result).await }`, and `result` lives across an `.await`, so the command's whole future is a *field* of that block's state machine. Creating the block allocates the struct — **not running yet is not the same as not occupying space**. Boxing puts the state machine on the heap and leaves the command's own future holding its arguments and a pointer.

The two compose and neither replaces the other: rule 1 decides *which thread* runs the body, rule 2 decides *whose stack* the state machine lands on. `connect_db` broke rule 1 and `get_databases_list` broke rule 2, and each produced the same symptom — `STATUS_STACK_OVERFLOW` (0xc00000fd) on `thread 'main'`, at launch or on the first connection, with no console to print it in a packaged build.

Debug never inlines the way `lto = "fat"` + `codegen-units = 1` does, which is why this is a release-only failure and why `tauri dev` cannot catch it. Reproduce with `npx tauri dev --release` — the same profile, but run from a terminal so the crash line is visible. Do not diagnose it by reasoning about which function looks big: five hypotheses were wrong before a trace (thread name + address of a local, appended to a file per line, since a windowed build has no stderr) named the real one in a single run.

Khoá của chính app — bearer token + khoá nhật ký MCP (`__mcp__`), device key của vault (`__vault__`) — LUÔN ở lại keyring, vì hai lý do: `audit_file::init` đọc khoá của nó ngay trong `app/setup.rs`, tức trước khi ai kịp gõ mật khẩu chính; và device key mở kho thì không thể nằm trong chính cái kho nó mở.

Nó chính là thứ để "ghi nhớ trên máy này" và "khoá khi rảnh" sống chung: ghi nhớ nghĩa là không hỏi lúc KHỞI ĐỘNG, còn khoá có chủ ý thì vẫn hỏi, kể cả sau khi restart. Thiếu cờ này thì device key nằm sẵn trong keyring khiến mọi lần khoá đều đi vòng qua được bằng cách thoát rồi mở lại app — và câu trả lời trung thực lúc đó là phải **chặn** hẳn tuỳ chọn auto-lock, tức giết một tính năng để che một lỗ hổng. Ghi cờ thất bại thì **fail closed**: xoá luôn device key. `relock` khai `#[serde(default)]`, vì một `vault.json` viết trước khi có trường này vẫn phải mở được.

- `stats/` — thống kê dung lượng/số dòng: `cells.rs`, `system_dbs.rs`, `probe.rs`, `database.rs`, `all_databases.rs`, `sizes.rs`, `row_count.rs`, `table_properties.rs`.
  - `table_properties.rs` (`get_table_properties`) là nguồn duy nhất của tab **Properties**. Nó đọc qua `execute_raw_sql_generic` chứ không qua driver row: funnel đó đã định tuyến sang kết nối được ghim khi có transaction thủ công, và đó là cách DUY NHẤT nhìn thấy một bảng tạm theo phiên. Mọi truy vấn phụ đều `.ok()`-dung thứ (thiếu `dbstat`, thiếu `sqlite_sequence`, chưa có dòng trong `pg_stat_all_tables`) — thiếu một số liệu phụ không được làm trắng cả bảng. DDL của Postgres dựng lại tại chỗ thay vì gọi `get_table_definition`: lệnh đó qualify theo schema của kết nối nên không bao giờ thấy được bảng nằm trong `pg_temp_N`.

- `database/` — cốt lõi của app. Những điều cần biết trước khi sửa:
  - `DbConnection` enum unifies `rusqlite::Connection` (wrapped in `Arc<Mutex<_>>`), `sqlx::PgPool`, and `sqlx::MySqlPool` behind one type. Every open connection lives in `state::ConnRegistry` (`AppState.connections`), keyed by `conn_id`; **there is no "active connection"** — every connection-bound command takes a `conn_id` argument. What the connections of one *server* share sits on an `Arc<ServerHandle>`: `db_type`, the connection config (`last_config`) and the SSH tunnel. `last_config` is what lets `restore_backup` reconnect transparently when a dump issues `USE <db>` (MySQL), and what `compare/` and the deep scan build their short-lived pools from.
  - The universal pattern in every command: lock `state.db_manager`, clone the connection handle out (`Arc`/pool clones are cheap), and **drop the lock before any `.await`** — `MutexGuard` is not held across awaits. Follow this pattern for new commands.
  - `execute_raw_sql_generic()` is the common dispatcher that runs a raw SQL string against whichever backend is active and normalizes the result into `{ columns, data }` JSON. Most commands build a SQL string and funnel it through this function rather than talking to `rusqlite`/`sqlx` directly.
  - SQL is assembled via string formatting (not parameterized queries) throughout — identifiers/values are manually quoted and escaped (e.g. `.replace("'", "''")`). This is inherent to a "raw DB browser" tool where table/column names are dynamic, but be careful preserving the escaping when touching this code.
  - Quoting is inconsistent by design across dialects: MySQL uses backticks, Postgres/SQLite use double quotes; several code paths build with backticks and `.replace("`", "\"")` for Postgres. Check the surrounding dialect-switch (`match db_type`/`match &conn_type`) before changing quoting logic.
  - `generate_alter_sqls()` translates a structured diff payload (added/dropped/renamed/modified columns, indexes, foreign keys) from the frontend's schema editor into a list of `ALTER TABLE`/`CREATE INDEX`/etc. statements, branching per dialect. `alter_table_schema` executes them; `preview_alter_schema` returns the same SQL as text without running it (used by the UI's "preview SQL" step before committing schema changes).
  - `split_sql_statements()` is the splitter used by `execute_multi_query` and `execute_query_stream` (i.e. "run all statements" from the SQL editor). It tracks quoting/escapes, `--`/`#`/`/* */` comments, Postgres `$$…$$` / `$tag$…$tag$` bodies, and MySQL's client-side `DELIMITER <token>` command (whose lines are consumed, never sent to the server). It also knows **trigger bodies**: while the delimiter is still `;`, a statement starting with `CREATE … TRIGGER` **and containing a `BEGIN` word** only ends at the `;` that directly follows `END` (`trigger_stmt_incomplete()` / `insideTriggerBody()`) — that is `sqlite3_complete()`'s rule, and SQLite needs it because it has no `DELIMITER`, so an exported trigger used to come back as a truncated `… BEGIN UPDATE t SET …;` and killed the whole restore. Requiring `BEGIN` is what keeps a Postgres trigger (`… EXECUTE FUNCTION f();`) and MySQL's single-statement form from swallowing the rest of the dump. Its frontend twin is `src/sql/statements.ts` — **keep the two in sync**: the editor decides what Ctrl+Enter runs and what gets highlighted, the Rust one decides what actually executes, and a mismatch means the user runs something other than what was highlighted.
  - `restore_backup()` replays a multi-statement `.sql` dump statement-by-statement, filtered to the selected tables, inside a transaction — three branches, **each on one connection it holds itself and none through a funnel**: MySQL (acquired connection + `SET FOREIGN_KEY_CHECKS`), Postgres (acquired connection, `BEGIN` then `SET CONSTRAINTS ALL DEFERRED`, a savepoint around every session-level statement so a rejected `SET` cannot poison the transaction with 25P02), SQLite (`PRAGMA foreign_keys OFF` on the handle). Postgres used to send `BEGIN` through `execute_raw_sql_generic`, which only held together because `should_route` opened a manual-transaction session on the caller's `conn_id` — i.e. the restore became the user's transaction. `cancel_restore(conn_id)` raises a flag checked between statements; the run rolls back and answers `cancelled: true` (on MySQL, DDL already run stays committed). It now **reuses `split_sql_statements()`** (the same splitter as the SQL editor) instead of the two inline `;`-only scanners it used to have, so `DELIMITER` blocks and `$$…$$` bodies survive — a `mysqldump --routines` file with triggers/procedures/functions replays correctly. After filtering, every `CREATE VIEW` is moved to the **end** of the list (stable partition, so their relative order survives). `CREATE VIEW` is validated when it runs, and dumps interleave views with tables alphabetically — sakila's `actor_info` sits right after `actor`, long before the `film` it selects from, so the whole restore died on MySQL 1146. The export side now writes views last, but dumps that already exist (and other tools' dumps) can't be fixed retroactively, so the runner has to tolerate the wrong order. Only `CREATE VIEW` moves: `DROP VIEW` staying put is harmless, and moving anything else could change what the dump means (a dump that INSERTs through an updatable view would break). The pre-filter that builds this list runs over **every** statement before the progress channel sends `start`, so anything quadratic in it shows up to the user as a frozen "preparing" bar: `TableMatcher` compiles **one** alternation regex for the whole restore (the old code compiled `\b<name>\b` per statement × per table — 50k × 22 ≈ 1.1M `Regex::new()` calls, measured at 20.3s vs 3ms), and `upper_head()` uppercases only the first 32 bytes instead of copying every multi-megabyte INSERT. Three helpers drive the per-statement decision: `is_session_level_stmt()` (statements that always run and whose failure is *not* fatal: `USE`, `SET …`, `CREATE DATABASE/SCHEMA` — a dump from another dialect will have `SET` lines the current server rejects), `stmt_mentions_table()` (word-boundary match against the selected tables), `use_db_name()` (target of `USE` for the post-restore reconnect). Deliberately **not** in the always-run list: `DROP DATABASE`/`DROP SCHEMA`, so importing a dump that starts with `DROP SCHEMA x` never wipes a schema the user didn't select. The `run_all` flag turns the table filter off entirely, and exists because that filter is **wrong** for a dump the app built itself: `TableMatcher` cannot see a table's name in every statement belonging to it — Postgres' `CREATE SEQUENCE IF NOT EXISTS film_film_id_seq;` holds no whole word `film` (an underscore is a word character), so filtering a generated dump drops the sequence and the `CREATE TABLE film (… DEFAULT nextval(…))` behind it fails. Only the copy-database path passes it (with an empty `tables`); a user-supplied file must keep the filter, since it is the only thing between "restore these four tables" and "replay the whole file".
  - **MySQL + prepared statements:** `sqlx::query()` uses the prepared-statement protocol, and MySQL rejects `CREATE`/`DROP TRIGGER|PROCEDURE|FUNCTION|EVENT` there with error **1295** (`This command is not supported in the prepared statement protocol yet`). Anything that may execute routine DDL must go through `sqlx::raw_sql()` (text protocol) — `restore_backup` does so unconditionally on MySQL, while `execute_raw_sql_generic` and `execute_query_stream` fall back to it (see `is_mysql_unprepared_error()`) so the SQL editor can create triggers/procedures too. Note MySQL also **implicitly commits on DDL**, so the transaction wrapped around a restore does not roll back already-created objects.
  - **Duplicate column names / `uniquify_columns()`:** every result row is shipped as a JSON object keyed by column name (`{ columns: [...], data: [{col: val}] }`), so two columns with the same name would collapse — `serde_json::Map::insert` overwrites and all but one value is lost with no error. `SELECT *` across a few joins hits this instantly (sakila's `film JOIN inventory JOIN store JOIN address JOIN city` returns five `last_update` and three `film_id`). Two rules, and **both** are needed at every one of the ~10 row-building sites: (1) run `uniquify_columns(&mut columns)` right after the column-name list is built and before any row is assembled, so repeats become `last_update (2)`, `last_update (3)`, … and the `columns` array the frontend receives carries the same suffixed names its `row[col]` lookups will use; (2) on Postgres/MySQL decode cells **by index** (`decode_pg_cell!(&r, i)`), never by name — `sqlx::Row::try_get(name)` resolves to the *first* column with that name, so a name-keyed loop returns that same first value for every repeat. The `decode_pg_cell!`/`decode_mysql_cell!` macros deliberately take an untyped `$col` so both a `&str` and a `usize` work; the `&str` form is only for hand-written introspection queries with known-unique aliases. The frontend needs no matching change, but `SqlEditor.tsx`'s result grid keys its `<th>`/`<td>` by **position**, not column name, because a stale/older backend can still send repeats.
  - `commit_changes` (the grid's "Save") runs its statements inside **one** transaction via `Exec` — one connection for the whole batch, `BEGIN`/`COMMIT`, `ROLLBACK` on the first failure. It cannot be wrapped around `execute_raw_sql_generic` instead, which acquires a new pooled connection per call. The batch is DML-only on purpose: adding DDL would make MySQL commit implicitly and defeat the rollback. When a **manual** transaction is already open it joins that one instead, leaving the commit point to the user.
  - **Postgres object kinds.** `get_table_definition` branches on `pg_class.relkind` before it builds anything: `'v'`/`'m'` return `CREATE [MATERIALIZED] VIEW … AS pg_get_viewdef()`, everything else falls through to the hand-built `CREATE TABLE` (columns + NOT NULL + DEFAULT + PK). Without that check it emitted a `CREATE TABLE` for every **view** too, so a re-imported Postgres dump grew real tables shadowing its views. Materialized views also need `pg_class.relkind = 'm'` to be listed at all — `information_schema.tables` does not contain them (not in the SQL standard), which is why they were invisible in the sidebar, the export dialog and compare; `get_tables` and `get_database_objects` both UNION them in as `VIEW`. A matview needs no `REFRESH` in a dump because `CREATE MATERIALIZED VIEW` populates on the spot and the dump writes it after the tables it reads, but its DROP must say `MATERIALIZED` — `dumpBuilder` detects that from the DDL text rather than threading a kind through.
  - **Postgres schema selection lives in `ConnEntry.current_schema`, not in command arguments.** One `conn_id` is one `(server, database)`, so it is also one current schema — the schema's home moved from a single global into one entry per connection when multi-connection landed. `connect_db` seeds it from `SELECT current_schema()` (`probe_pg_schema`), `open_database` probes it for the connection it mints (each database has its own schemas), `disconnect_db` drops the entry with it, and `set_current_schema` (the Sidebar picker) sets it after checking the name exists. All of them return the effective schema, and the frontend must read it from there rather than from its own picker state: it is part of the localStorage scope (`scopeKey`), so a value the backend disagrees with keys tabs wrongly. `list_schemas` returns `[]` on MySQL/SQLite, which is how the UI decides whether to show the picker at all. Three helpers carry it: `ConnCtx::schema()` (what every call site reads — it defaults on the way out, so a site can no longer forget to default and silently query `public`), `pg_schema_of()` (where that `public` default is spelled, once), `sql_str()` (escape for a `nspname = '…'` literal), and `qualified()` — the twin of `compare/ident.rs` and of `datagen/`'s own copy, which only qualifies on Postgres so MySQL/SQLite output is unchanged. `datagen/` gets the schema from `active_conn()` (which already returned the dialect) because the five functions needing it are internal, not commands. **When adding a path that builds SQL from a table name, qualify it** — the write paths carry no `'public'` to grep for, so a missed one silently targets `public`, and `get_primary_key_columns` reading a different schema than `commit_changes` writes to is a wrong `WHERE`, i.e. wrong rows changed rather than an error. `docs/postgres-schema-support-plan.md` §4.2 lists every call site. Emitted DDL is deliberately **not** qualified so a dump can be restored into a differently-named schema; `dumpBuilder`'s header carries `CREATE SCHEMA IF NOT EXISTS` + `SET search_path` instead (only when the schema is not `public`, so ordinary dumps are byte-identical to before). One thing that escapes it: `pg_get_indexdef()` is Postgres's own output and always includes the source schema.
  - MySQL **scheduled events** come from `information_schema.EVENTS` (in `get_database_objects`, empty on the other two dialects) and their DDL from `SHOW CREATE EVENT` via `get_object_definition(kind = "event")`. The dump writes them in the same `DELIMITER $$` block as routines and triggers, because an event body (`DO BEGIN … END`) carries its own `;`.
  - `ai_chat` vẫn là stub echo lại prompt; UI "AI Copilot" (`AiAssistant.tsx`) chưa nối vào model thật. Nó nằm ở `app/ai.rs`, không ở `database/`, vì nó không chạm database nào.
  - **Ba stub chết đã bị xoá** (`export_table`, `import_dbeaver`, `restore_backup_old`) cùng `export.rs` và dependency `flate2`. Dump được dựng ở frontend (`utils/dumpBuilder.ts`), còn `import_new_table`/`import_table_data` là code THẬT — chúng nằm ở `database/commands/row_write.rs`, đừng nhầm với đám stub cũ.
- `tx/` — **manual transaction mode** (auto-commit toggle, Commit/Rollback, isolation level, savepoints), driven by `TxControl.tsx` on the title bar. The things to know before touching anything that runs SQL:
  - **A transaction belongs to the connection, not to a tab.** Sessions are a `HashMap` keyed by `conn_id` (`TX_REGISTRY` in `tx/session.rs`), so there is one session per open connection and two tabs on the same connection share it. That is why the control lives on the title bar scoped to one connection (`TxControl` takes it as a `connId` prop and **drops `tx-state-changed` events carrying any other one**), rather than each tab's toolbar owning a transaction. `tx_status` therefore takes a `conn_id`; the one question that is not per-connection is `tx_any_pending()`, which the window-close guard asks because closing the window kills every session at once.
  - **The naming here is constrained by CodeQL, and the constraint is not obvious.** The accessor is `conn_scope_id()` and the map is `TX_REGISTRY`/`ConnScopeId` — **do not put `session`, `key` or `uuid` back into any of those names.** CodeQL's sensitive-name heuristic (`SensitiveDataHeuristics.qll`, `maybeAccountInfo`) matches `session.?(id|key)` and any `uuid` substring, which makes the function a taint *source*; because the returned `&str` borrows `conn.id` while the same `conn` carries the DB handle in `conn.kind`, the analysis (which does not separate two fields of one struct) then reports `Exec::run` and `sqlite_raw` as `rust/cleartext-storage-database` — high severity, and a false positive every time: `mint_id()` is a random v4 UUID, never derived from the config, and the id never enters a SQL string. Renaming `session_key` -> `session_id` was tried and **could not work**, since `id` and `key` are alternatives inside the same group of that regex. The domain word "session" is fine everywhere it does not sit next to `id`/`key` — `Session`, `session_for`, `tx/session.rs` are all clean. `terminal/{local,ssh}.rs` still take a `session_id` **parameter**: that is the IPC contract with the frontend, it reaches no database sink, and renaming it would break `dbHelper`.
  - **Every SQL path must ask the session.** `should_route()` is checked at the top of `execute_raw_sql_generic`, `run_bound_query` and `stream_one_statement` — **a new execution path must do the same**. Routing only some of them means a grid refresh reads through a different pooled connection and cannot see the uncommitted rows, which reads to the user as lost data. Routing is by design a *global* lookup (a module-level `static`, not `AppState`): those funnels receive a `&DbConnection` and no `AppState`, and there is only ever one session to find.
  - This is why `sqlite_raw` / `pg_raw` / `mysql_raw`, `*_bound` and `*_stream` exist as separate functions: the identical body runs whether the connection came from the pool or from the pinned session. Duplicating them would duplicate the two rules every row-building site must follow (`uniquify_columns` first, decode **by index**).
  - **Auto-commit OFF issues `BEGIN` from the client**, JDBC-style, because Postgres has no server-side autocommit flag. A hand-typed `BEGIN` also opens a session (`should_route` returns true for it) — before this existed it went to a pooled connection and did nothing but leave that connection *idle in transaction*.
  - `tx_effect()` classifies every statement so the pending counter cannot lie: it catches the user's own `COMMIT`/`ROLLBACK`/`SAVEPOINT` and MySQL's **implicit commit on DDL**. It reads only the first 4 tokens — it runs on every statement, including bulk INSERTs whose text is megabytes. Postgres's aborted state (`25P02`) is detected here too and surfaced as a boolean, never compared as text on the frontend.
  - `is_write_stmt()` decides what the counter counts. A `SELECT` **does** open the transaction (that is how you read back what you just wrote, and the only way an isolation level means anything) but is **not** counted — the number next to Commit promises "this many changes are waiting". Unknown shapes (`WITH …`, `CALL …`) count as writes: over-reporting costs a needless rollback, under-reporting loses data.
  - The session also keeps the **SQL text** of those write statements (`pendingSql`) for the pending-changes dialog, capped per statement and in total, with a `sqlTruncated` flag rather than silently showing less. Each savepoint records the counter value at the time, so `ROLLBACK TO` rewinds both the count and the log exactly instead of guessing.
  - **SQLite is not pinned**: `DbConnection::Sqlite` is already one shared handle, i.e. already one session. Only the state machine applies, and the isolation-level select carries `DEFERRED/IMMEDIATE/EXCLUSIVE` instead of isolation levels.
  - **A write path outside the three funnels must ask `use_session()`, never `is_open()`.** A transaction does not exist until its first statement runs, so a command that checks `is_open()`, finds `false` and takes its own connection commits behind the user's back while the mode still says "manual" — that was a real bug in `commit_changes` (the grid's Save), `drop_table` and `truncate_table`. `run_fk_wrapped()` is the shared shape for "a couple of statements on one connection, with FK checks optionally off around them" and gets this right.
  - Lifecycle, all deliberate: `connect_db`/`disconnect_db` roll back and reset; **`open_database` refuses nothing** — it *adds* a pool under a new `conn_id` instead of swapping the pool under a live one, so a transaction open on the current database keeps running while the user works in another (this is why `switch_database`, which had to refuse whenever the connection held uncommitted work, was deleted rather than fixed); `restore_backup` and `generate_data` refuse whenever manual mode is on at all, since they commit periodically by design and so can never join the user's transaction; the IAM refresh task skips a pool swap while one is open. The frontend blocks window close via `onCloseRequested`.
  - State reaches the UI as a `tx-state-changed` **event** (the `AppHandle` is parked in the module at setup), not as a field added to every command's response.
- `compare/` — compares **two** databases (structure and data), driven by `DbCompareDialog.tsx`. The one thing to understand before touching it: a side may point at a database no connection is open on, so each is resolved separately in `resolve_side()` — it **reuses the connection identified by `conn_id`** when the side names the same place (no re-auth, which matters for AWS IAM tokens) and otherwise opens a short-lived pool from that server's config with the database/file overridden, exactly like `get_all_databases_stats`' deep scan. Every ad-hoc pool is built with `DbConnection::adhoc`, so `ConnId::Adhoc` makes it **structurally impossible** for `should_route` to pin it as the user's transaction session — that was a real bug once (§0 of `docs/multi-connection-plan.md`), and it is now a property of the type rather than a rule to remember. Ad-hoc pools are closed by `Resolved::close()` before the command returns; SQLite is opened `SQLITE_OPEN_READ_ONLY` so a mistyped path can never create an empty file. Metadata goes through `execute_raw_sql_generic` (now `pub(crate)`, along with `apply_ssh_tunnel`/`apply_iam_password`) rather than re-decoding driver cells. Three commands: `compare_schemas` (per-table/column/index/FK diff + sync SQL), `compare_data_overview` (row counts per table, cheap triage), `compare_table_data` (row-level diff by key + INSERT/UPDATE/DELETE script). Notes: type comparison is normalized (`norm_type` folds `int(11)`/`INT` and `character varying`/`varchar` so MySQL 5.7-vs-8 or MySQL-vs-Postgres doesn't report noise, while lengths still count); `values_equal` only loosens number-vs-numeric-string (`DECIMAL` arrives as a string from sqlx) and compares two strings exactly, so a real difference is never hidden; every `DROP`/`DELETE` is emitted **commented out** unless `includeDrops` is set, and a changed index/FK comments its DROP *and* CREATE together so a half-applied script can't happen. **Language split** (deliberate): errors and the `warnings` array are Vietnamese and translated via `backendErrors.ts` (`dbHelper` maps `warnings` too — `translateResultErrors` only covers `message`/`error`), but comments inside the generated SQL script are **English**, because that script is an artifact the user pastes into a migration/CLI, not UI text.
- `datagen/` — bulk **test-data generation** (dbForge-style Data Generator), driven by `DataGeneratorDialog.tsx`. Four commands: `get_generation_targets` (tables/columns + a *suggested* generator per column + the FK-safe insertion order), `preview_generated_data`, `generate_data` (progress + cancel over a `Channel`), `cancel_data_generation`. The decisions worth knowing before touching it:
  - **Values are produced only in Rust — there is no TS twin, on purpose.** Preview runs the same code path as the real run (minus the writes), so what the user sees is what gets inserted. One deliberate exception: a FK column whose parent is still empty would preview as a column of NULLs (the parent is only filled during the run), which reads as a broken generator — `estimate_fk_pool` therefore shows the keys the parent is *about* to get (replaying the parent's generator, or continuing from `MAX(key)` for an auto-increment parent) and the result carries a warning saying the values are an estimate. The preview call sends the **whole** spec, not just the previewed table, because that estimate needs the parent's spec. `split_sql_statements` ↔ `sql/statements.ts` and the Rust error literals ↔ `backendErrors.ts` are already two hand-synced pairs; a third one existing only for preview would drift silently. `utils/dataGenHelper.ts` therefore holds spec plumbing (labels, option-field descriptions, validation) and no generators — its one small twin, `templateSpace`, feeds a warning and never generation.
  - **Determinism**: a seeded xoshiro256\*\* written here (~30 lines) — no `rand`/`fake`/`rand_regex` crate, no OS entropy, no clock, so the same spec + seed replays byte-identically. Each column draws from its **own** substream (`mix_seed(seed, table, column)`); one shared stream would make editing column 3 shift the values of every later column and the preview jump on every keystroke. `regex` (the crate) can only match, not sample, so the supported regex **subset** is parsed and sampled by hand (`parse_regex`/`sample_regex`), and anything outside it (`(?…)`, backreferences, anchors, `{n,m}` over 64) is rejected while the column is configured rather than at row 1,000,000.
  - **Writing**: one dedicated connection per run (`Exec`), because `execute_raw_sql_generic` acquires a *new* pooled connection per call, so `BEGIN` / `SET FOREIGN_KEY_CHECKS` issued through it would land on a different session than the INSERTs. Batched multi-row INSERT (500 rows, less for wide tables) with a periodic COMMIT, **plus a COMMIT at the end of every table** — a FK column reads its parent key through `execute_raw_sql_generic`, i.e. from another pooled connection, which cannot see rows still uncommitted in ours, and an auto-increment parent key exists *only* in the database (the column is generated with `skip`), so without that commit generating a parent and its child in one run always failed. FK values are the union of "what the parent table holds" and "what this run generated for it" (the latter covers a reference cycle, where the parent is generated after the child); there is deliberately no "only existing values" switch, because no honest description of it survives those two requirements. Constraint-disabling order is dialect-specific and not interchangeable: SQLite `PRAGMA foreign_keys` is a **no-op inside a transaction** (so it goes first), Postgres `SET CONSTRAINTS` is only valid **inside** one (so it goes after BEGIN, and again after every periodic commit). "Delete existing rows" uses `DELETE`, not `TRUNCATE`, because MySQL implicitly commits on DDL and would strand what the transaction already wrote.
  - Error messages name `table.column` so none of them needs an outer wrapper — a wrapped Vietnamese message could not be matched by `backendErrors.ts`, whose new `nested` flag exists for the one genuinely nested case (a regex parser error inside "Regex của cột '…' không hợp lệ: …").
  - Pure helpers (PRNG, template/regex expanders, Luhn, topo-sort, `type_family`, MySQL enum parsing) are verified with the standalone-`rustc` trick described above rather than by a cargo test.
- `ssh/` — SSH, hai nhiệm vụ tách rời. `auth.rs`: `connect_and_auth()` (password hoặc private key; `check_server_key` chấp nhận tất cả — không có `known_hosts`), dùng chung với SSH terminal. `tunnel.rs`: `SshTunnel::open()` bind `127.0.0.1:0` và bơm mỗi socket nhận được qua một kênh `direct-tcpip`. `database::apply_ssh_tunnel()` là entry point mọi caller dùng: nó trả về config đã đổi `host`/`port` sang cổng đã forward, kèm handle của tunnel. **Thả handle là đóng cổng**, nên ai sở hữu kết nối cũng phải sở hữu tunnel — `ServerHandle.ssh_tunnel`, dùng chung cho SQL lẫn Redis.
- `redis_db/` — transport config (the rest of the file is the Redis browser itself):
  - **TLS is a mode, not a switch.** `redis_ssl_mode()` folds the UI's `sslEnabled` + `sslMode` into DISABLED / REQUIRED / VERIFY_CA / VERIFY_IDENTITY. An *absent* mode with the switch on means VERIFY_IDENTITY, because that is what the old switch-only profiles actually did (`rediss://` verifies fully under rustls) — mapping them to the weakest mode would silently downgrade every saved connection. PREFERRED is not offered (Redis has no STARTTLS negotiation) and is mapped up, not down. Its twin on the frontend is `REDIS_SSL_MODES` in `ConnectionManager.tsx`.
  - REQUIRED is the `#insecure` URL fragment and VERIFY_CA is `set_danger_accept_invalid_hostnames`; **both need the `tls-rustls-insecure` feature** on the `redis` crate or the connection fails at handshake time with a config error. The hostname flag must be applied **after** `Client::build_with_tls()` — that call rebuilds `tls_params` from the certificate files and would drop a flag set before it.
  - CA / client cert / client key come from the same `sslCaPath`/`sslCertPath`/`sslKeyPath` fields as Postgres and MySQL, but redis-rs wants **file contents**, not paths, so they are read into `TlsCertificates` (a half-set mTLS pair is rejected in the form's own words rather than left to fail as an opaque TLS error).
  - **A Redis `ServerHandle` keeps the TUNNELED config** — unlike SQL, which keeps the original and reopens a tunnel every time it builds a pool. Redis reconnects far more often (db-index switch, Pub/Sub, Profiler each open a new socket) and the tunnel is already alive on that very handle, so `select_db_inner` and `dedicated_client` reconnect through it instead of opening a second one. Consequence worth knowing: over a tunnel the certificate is presented for `127.0.0.1`, so VERIFY_IDENTITY cannot work and the SSL tab says so.
  - **Xuất / nhập keyspace theo prefix** (`redis_dump_keys` / `redis_restore_keys`, driven by `RedisTransferDialog.tsx`, file format in `utils/redisTransfer.ts`). The decisions worth knowing:
    - **DUMP/RESTORE, not a readable JSON serializer.** Both existing read paths are lossy: `fetch_elements` puts every element through `lossy_text` (non-UTF-8 bytes become U+FFFD — that is what the `binary` flag locks editing for) and `redis_get_key` truncates strings at `STRING_PREVIEW_MAX`. An export built on those corrupts data silently, which is the worst possible failure for a backup feature. A DUMP payload is Redis's own bytes: exact, and it covers the types the app has no editor for (ReJSON, TimeSeries, vector set). The cost, stated in the dialog: the payload carries an RDB version footer, so it only restores into a Redis of the same version **or newer**.
    - **Reads are pipelined, writes are not.** `DUMP` of a missing key returns Nil rather than an error, so a whole batch can never be broken by one key. `RESTORE` can (BUSYKEY), and a pipeline reports only the *first* error while the server still executes the rest — so re-running the batch to attribute errors would hit BUSYKEY for keys it had just created and report them as "already existed". `redis_restore_keys` therefore runs key by key; the frontend batches at 200 so progress still moves.
    - `payload` travels as **base64**, not as the byte array `redis_get_key` uses for `bytes` (~3× smaller over IPC, and it is what goes into the text file). `base64` is a direct dependency for this, already in `Cargo.lock` beforehand.
    - BUSYKEY is counted as **skipped**, not failed — an ordinary import into a db that already holds some of the keys would otherwise look like thousands of errors. `failed[].error` is Redis's own English text and deliberately does **not** go through `backendErrors.ts`.

### Frontend (`src/`)

- `App.tsx` — top-level state owner: active connection, the tab list (`TabInfo[]`, each tab is either a `table` or a `query`), theme, and all the global Import/Export/Backup-Restore modals (these are large inline JSX blocks rather than separate components — follow that pattern if extending them, or consider extracting if they grow further). Cross-component signals that don't fit the props tree use `window` `CustomEvent`s: `table-renamed` and `database-restored` (dispatched after imports/restores so `Sidebar`/`DataGrid` can refetch).
  - **The SQL dump is built in `utils/dumpBuilder.ts`** (`buildDump`), called both by `handleExportDatabase` here and by Connection Manager's Backup button — the Rust `export_multi_tables` it replaced treated views as tables, wrote one `INSERT` per row and had no routines, so every fix made for the dialog missed the Backup path. DB access is injected as a `reader` param (`dbHelper` matches the shape) so the module imports no `@tauri-apps/api` and the statement order is unit-tested (`dumpBuilder.test.ts`). That **order is load-bearing**: sequences → base table (DDL, indexes, comments) → data → deferred FK/UNIQUE/CHECK (`ALTER TABLE ADD CONSTRAINT`, only after *every* table exists) → `setval()` (reads `MAX()` of the rows just inserted) → views → routines → triggers. `get_table_ddl_extras` supplies the per-table extras: nothing for MySQL (`SHOW CREATE TABLE` has it all), indexes for SQLite, and index/FK/CHECK/comment/sequence for Postgres, whose `CREATE TABLE` is hand-built from columns + PK only. Routines and triggers come last because their bodies read tables and a trigger may call a function; on MySQL they are wrapped in one `DELIMITER $$` block (`wrapMysqlDelimiter`), and every DDL goes through `stripDefiner()` — a kept `DEFINER=user@host` makes the restore fail with error 1227 for anyone else. Data fidelity lives here too: `generated`/identity columns are dropped from the INSERT column list (MySQL 3105) and binary columns are written as `X'..'` / `'\x..'::bytea` via `isBinaryType()`, because the backend ships a BLOB as a byte **array** that would otherwise be stringified into `'[137,80,...]'`. Triggers follow their table in `ExportDatabaseDialog` (ticking a table ticks its triggers, like `mysqldump`); the dialog groups the list by kind because 23 sakila tables pushed routines below the fold and they looked missing. Older text, still true of the table/view part: every base table (DDL + data) first, then every view. `CREATE VIEW` is validated when it runs, so a view emitted in the sidebar's alphabetical order landed before the tables it selects from and the re-import died on MySQL 1146 — `actor_info` is the second name in sakila. Views carry `DROP VIEW`/`CREATE VIEW` (never `DROP TABLE`, which cannot drop a view) and **no data** (`INSERT` into a non-updatable view fails, and the rows are already in the base tables). Between views the order comes from `orderViewsByDependency()` in `exportHelper.ts` — a view may read another view. `ExportDatabaseDialog` therefore passes `views: string[]` alongside `tables`; `dbHelper.getTables()` is where the table/view distinction comes from.
  - **A dump written to a folder is streamed**: `writeDump(spec, reader, emit)` emits it a table and a PAGE of rows at a time, every chunk ending between two statements, into `fileSave.ts`'s `saveDumpToFolder` → Rust `export_sink.rs` (`.part` file renamed on close, gzip via `flate2`). `buildDump` is `writeDump` collected into one string, byte-identical to before — the tests use it and the copy-database path needs the whole string for `restore_backup`. Add a new section to the dump through `parts` + `flush()`, never by returning text, or it lands out of order.
  - `buildSql()` batches rows into multi-row `INSERT`s (500 rows / 200k chars per statement). One INSERT per row made a sakila dump ~50,000 statements, and `restore_backup` runs each one as its own round trip. Its reader twin is `parseInsert()` in `dumpPreview.ts` — that one walks tuples by index, not by re-slicing the remainder, because these statements are now hundreds of KB (`exportHelper.test.ts` pins the round trip).
  - Table/view names are detected from a dump in exactly one place: `parseDumpTableNames()` / `dumpStatementObject()` in `dumpPreview.ts`. There used to be four copies of that regex (both dialogs, the count memo, and a Rust `parse_backup_tables` command — since deleted, it had no caller left and its stale regex would have silently dropped views/routines/triggers for whoever called it next), and none of them matched `CREATE VIEW`/`DROP VIEW` — a view then never reached the selected-tables list, so `stmt_mentions_table` on the Rust side silently dropped its statements.
  - Both restore dialogs (`ImportDatabaseDialog`, `ConnectionManager`'s Backup/Restore) split the dump **once per file** into a precomputed array (`table`/`kind`/`skipped`/`commentOnly`). The count and the previews only read that array. Do not add a `useMemo` over `sqlText` keyed on the selection — that is what made every checkbox tick re-scan 10M characters.
- `utils/dbHelper.ts` — the only place that calls `invoke()`. Defines the shared TypeScript types (`DbConnectionConfig`, `TableItem`, `ColumnInfo`, `SchemaInfo`, `GridChange`) that describe the JSON contract with `database/`. When the Rust side's JSON shape changes, update the corresponding method here.
- **Per-connection localStorage: always scope through `utils/connKey.ts`.** Never key user state by `dbName` alone — it is `config.database || config.sqlitePath` (`dbHelper.connect`), so two servers hosting a database of the same name shared one key, and every Redis server collapsed into `db0`. `connKey(config)` identifies the **server** (`mysql:host:port`, or the normalized SQLite path; credentials excluded, SSH-tunnel rewriting happens in Rust so the real host is used), `scopeKey(config, db, schema)` identifies server + database + Postgres schema. Tabs (and the SQL auto-saved inside them) use `scopeKey` via `tabsStorageKey()`, because a tab list belongs to one database and — on Postgres — to one schema of it. **The key gained levels over time, so writing and reading are asymmetric**: only the newest spelling is ever written, while `tabsStorageKeyCandidates()` reads the newest, then the schema-less key, then `legacyTabsStorageKey()`, so an upgrading user's workspace is carried forward instead of vanishing. The `:schema` suffix is appended **only when the schema is not `public`**, which is what keeps every pre-schema key spelled identically. Query history is stored as one list and *filtered* at display time (see below). That write is the biggest thing in localStorage (draft SQL × tabs × databases), so it is wrapped in a try/catch that retries without the inactive tabs' drafts on `QuotaExceededError`.
- `utils/queryHistory.ts` — the store behind the SQL editor's history drawer (`sql_query_history` / `sql_saved_queries`). Every mutation is a read-modify-write against localStorage, **never a write of component state**: each query tab mounts its own `SqlEditor` holding its own copy, so writing state back resurrected entries another tab deleted. After each write it dispatches `sql-history-changed` so the other mounted editors reload. Entries carry `conn` (a `connKey`) + `db`, and the drawer filters them through `matchesScope()` with three scopes — `db` (default), `conn` (every database of that server, so a `USE` timeline stays whole), `all` — persisted in `tf_history_scope`. Both fields are optional and an entry without them matches **every** scope, which is how pre-existing history survives; that is also why `clearHistory()` deletes untagged entries only at scope `all` (deleting them from one scope would silently delete them from the others). The 500-entry cap is applied **per `conn`** (`trimHistory`) so a busy connection cannot evict the others. A row is written when the run *starts* (`addHistoryEntry` returns its id) and the outcome is patched on when it finishes (`recordHistoryResult`: `ok`/`ms`/`rows`/`affected`/`error`, the error truncated to `ERROR_MAX_LENGTH`) — `ok` stays **undefined** for a run the user stopped and for every row written before this existed, so the drawer shows no status icon rather than a wrong one. Re-running the statement at the top of a connection's history reuses that row (moved back to the top, result cleared) instead of adding a duplicate, which is why the array order can be relied on as newest-first.
- `utils/redisTransfer.ts` — the file format behind Redis **export/import of a keyspace by prefix**, built on the same pipeline as `dumpBuilder.ts`: the content is assembled here and DB access is injected (`RedisExportReader` / `RedisImportWriter`, which `dbHelper.redisScanKeys`/`redisDumpKeys`/`redisRestoreKeys` match), so the module imports no `@tauri-apps/api` and the format is unit-tested (`__tests__/redisTransfer.test.ts`). Format is **NDJSON**: a header line, one line per key (`{key,type,ttlMs,payload}` — the *same* field names `redis_dump_keys` returns and `redis_restore_keys` accepts, so nothing is renamed between Redis, the file and Redis again), then a footer line carrying the count. Three things are load-bearing. (1) **The footer is only written for a complete export** — hitting `EXPORT_KEY_CAP` or being stopped deliberately leaves it out, and `parseRedisExport` reports that as `truncated`, which is the only way an incomplete file can be told from a whole one. (2) **A bad line does not fail the file**: it goes into `badLines` and the rest still imports, because "the whole 100k-key file is void because line 4 is broken" is the worst outcome available. (3) `prefixPattern()` escapes glob metacharacters by delegating to `folderMatchPattern()` rather than carrying its own copy — without escaping, prefix `log[1]:` scans for keys starting with `log1:`, i.e. exports the wrong set with no error; `patternToPrefix()` is the reverse (the key browser's search box holds a *pattern*, the dialog takes a *prefix*) and returns `''` rather than guess when the body still holds glob syntax, since `prefixPattern` would then escape it a second time. Entry points: the key-list header's ⇅ button (current search pattern) and a key-tree folder's context menu (a real prefix, so no guessing). Adding a `redis_*` command means classifying it in `utils/safeMode.ts` too — `safeMode.test.ts` reads `dbHelper.ts` and fails on an unclassified one.

- `utils/safeMode.ts` — **an action that runs several backend commands must go through `runApproved()`, not through the per-call gate.** `approveCommand()` sits in front of every `invoke()` (`dbHelper`'s single local funnel), which is correct as long as one user action is one command — true of `commit_changes`, `restore_backup`, `generate_data` and every other write until the Redis keyspace import, which calls `redis_restore_keys` once per batch of 200 and therefore asked 50 times for 10,000 keys. Nobody answers 50 dialogs; they switch Safe Mode off, so the cost of the feature becomes the loss of the guard. `runApproved(cmd, connId, detail, run)` asks **once** and holds a door open for the duration: keyed on the exact command *and* connId (an approved import cannot carry a `redis_flush_db`, or the same command on another connection, through with it), closed in a `finally` so a run that throws does not leave it open, and depth-counted so a nested or concurrent run ending does not close the outer one's door. It deliberately does **not** remember the answer afterwards — there is no "don't ask again". The `detail` string is passed in already translated (`SafeModeRequest.detail`, rendered above the command name by `SafeModeGate`) because a once-per-run question has to say *what* it is approving — "import 10,000 keys, overwriting existing" — and this module has no `t()`.

- `components/`:
  - **Buttons are `className="btn btn-secondary"` / `"btn btn-primary"` — both classes.** `.btn` alone carries the geometry (28px height, 8px radius, 11.5px/600); `btn-secondary` on its own only sets colours, so the button renders at the browser's default size and squared corners. Same trap for inputs: the shared style matches `input[type="text"]`, so an `<input>` written without a `type` gets no background or border at all.
  - **Inline `style={{…}}` is for values computed at runtime; anything static belongs in `index.css`.** The line is real but eroding — 1982 inline `style` props against 2934 `className`s, and the gap only closes when someone moves a batch (the sixteen constants `Sidebar.tsx` used to carry were one such batch). Two halves to the rule. (1) **Never write a bare colour, font or radius inline.** The app swaps themes through `[data-theme='dark']`/`[data-theme='light']` over 29 `--win-*` tokens, so a hardcoded `#0284c7` is correct in at most one of the two themes; the 182 such literals still in the tree (73 of them in `WhatsNewModal.tsx`) are a backlog, not a precedent. Use `var(--win-…)`, and a hex **only** as its fallback (`var(--win-danger, #ef4444)`, 51 uses). (2) Inline is the right answer for a value the render computes — a measured width, a `transform` from drag state, a per-row colour from data — and the wrong one for `display: flex; gap: 6px`, which is a class by the third time you type it; a static object literal is also rebuilt every render, so it defeats memoization in any child that receives it as a prop.
  - **`Modal.tsx` — the shared dialog chrome. Build every new dialog from it; do not hand-roll an overlay.** It owns the backdrop (`rgba(0,0,0,0.6)` + `blur(2px)`), the card (6px radius, `--win-border-strong`, `0 20px 40px rgba(0,0,0,0.4)`), and the title bar (`12px 16px`, `--win-bg-tab-bar` fill, 12px/600 title, `×` close), plus `ModalBody` (padding 16, gap 14, scrolls) and `ModalFooter` (padding 12/16, same fill, right-aligned). It always renders through a **portal**, because dialogs are frequently mounted inside panels using `backdrop-filter` (`.card`, `.connection-card`) and that property makes a new containing block, so `position: fixed` would only cover the panel. Esc and backdrop click both close (`closeDisabled` suppresses both plus the `×` while an operation runs); a dialog needing Enter-to-submit keeps its own key handler (see `ConfirmDialog.tsx`). All 23 dialogs now go through it. Two exceptions render their chrome from CSS instead and **must be kept in sync by hand**: `.ctm-*` (`CreateTableModal`) and `.cm-modal*` (`ConnectionManager`'s 3 modals + the About card's backdrop) in `index.css` — both carry a comment pointing back here. `zIndex` is passed per call site rather than centralised, deliberately: the old values encode which dialog may sit above which (`ConfirmDialog` at 10001 above the 9999/10000 dialogs it is opened from; Sidebar's at 999999 above its 99999 context menu), and normalising them is a separate change.

  - `Sidebar.tsx` — table/view list, search, per-table context menu (rename/drop/import/export), "new query" and "backup/restore" entry points. **Three things keep it usable at 2500 tables, and each solves a different half of the cost — do not undo one thinking another covers it:**
    - **`content-visibility: auto` on `.sidebar-row`** is the lazy renderer: the browser skips style, layout and paint for any row not near the viewport. It is the right tool here *because the rows are not a uniform height* — an expanded row carries a whole `TableDetailTree` — and `contain-intrinsic-size: auto 26px` makes the browser remember each row's real size once it has been rendered, which is exactly the bookkeeping a JS windowing library would have to do by hand. The 26px is measured from `.sidebar-row > .sidebar-item`, so those two rules move together.
    - **Rows render a chunk at a time** (`useChunkedList`, 150 at a time, grown by an `IntersectionObserver` sentinel). This is the half `content-visibility` cannot touch: React building the elements and the browser building the DOM nodes, paid in full on every rebuild — a keystroke in the search box, expanding a row, an arrow key. Growing forwards rather than windowing keeps the DOM in document order, so `scrollIntoView`, focus and find-in-page still work. Two things it has to carry: `minCount`, because ↑ from the first row wraps to the LAST one and there must be a row there to scroll to; and a reset when the filtered list changes, done **during render** (the `reconcileLayout` pattern) rather than in an effect.

Same trade the ER canvas makes for hover. Two traps came out of this: the classes were inline styles before, so the CSS that replaced them has to win on specificity (`.workspace-container .sidebar-item.is-on`, placed after `.active`); and `applyRowClasses` takes the selection as an ARGUMENT, because `selectionRef` is filled by a passive `useEffect` and reading it from a `useLayoutEffect` sees the previous render's value — which lit two rows at once.

  - `DataGrid.tsx` — paginated table data view+editor; edits are buffered client-side as `GridChange[]` and flushed via `dbHelper.commitChanges`. Its bottom bar switches four panes (`GridViewMode`): Data, Structure, Chart, **Properties**.
    - **There are two row grids, `DataGrid` and `SqlEditor`'s result grid, and merging them was considered and rejected.** They look identical because the CSS *is* shared (`.grid-table`, `.grid-table-container`, `tr.selected`, `.grid-row-index`, `.grid-cell-dirty`), and they behave identically on a click because that rule set is shared too — but underneath they agree on nothing, and on all three axes the disagreement is structural:
      - **Where the rows come from.** `DataGrid` pages *and* sorts on the SERVER (`getTableData` with `LIMIT`/`ORDER BY` plus keyset cursors); the result grid holds the whole result in memory and pages and sorts on the client (`sortedResults1/2`).
      - **What identifies a row**, which follows from that and is not a free choice either way. `DataGrid` keys a selection by the **primary-key value** (`__tempId` for a not-yet-inserted row) because changing page or sort refetches, so no row object survives. The result grid keys it by the **row object**, because a query result has no primary key to key it by — it can be a join, an aggregate or a bare `SELECT 1` — and the object works precisely because the sort memo sorts a COPY, so sorting and paging hand back the same objects.
      - **Whether the table is known.** `DataGrid` always knows its table. The result grid has to INFER it (`sql/editableResult.ts`), which is the gate on cell editing and on the INSERT/UPDATE copy formats; a result that maps to no single table with a single-column PK gets neither.
      A shared component would have to carry both sides of all three behind flags, and the flags multiply — the shared thing becomes a switchboard, and every bug in one grid gains a path into the other. What IS shared is pulled out as **pure** functions instead, which is the same line `copyAs.ts` and `menuPosition.ts` already sit on: `utils/rowSelection.ts` holds the click→selection decision table (`resolveRowClick`, `resolveRowContextMenu`), because "Shift does not move the anchor" is a judgement call and a judgement call needs one place to be read — it was written twice, verbatim, before it lived there.

And the result grid's context menu renders through a **portal** into `document.body`: its first home was inside `.grid-table-container`, which scrolls, and an `overflow` ancestor clips a `position: fixed` descendant as soon as anything between the two establishes a containing block (`body` here carries `backdrop-filter`, which does).

- `components/er/` — the ER diagram: a pan/zoom **canvas** (one `<canvas>`, no DOM per table), driven by `ERDiagramTab` (Sidebar → ER Diagram). Two Figma-style tools, `select` and `hand` (`V`/`H`, Space borrows `hand` from either, middle-drag pans in both, `Shift`+`0`/`1`/`2` reset/fit/zoom-to-selection). `erViewport.ts` holds every bit of the math as pure functions **because a bug in it shows up as content in the wrong place, and there is no element inspector to find it with** — `erViewport.test.ts` pins the cursor-anchored zoom, the LOD thresholds and the culling rectangle; `erScene.test.ts` pins hit testing, the raster scale and the bitmap cache key.
  - **It was HTML cards over an SVG connector layer, and the rewrite is the whole story of this directory.** A profile at 320 tables / 537 FKs (`scripts/make-er-mock-db.mjs` writes such a database) put 340ms of 6,463ms of main-thread time in app code — **almost none of the cost was JavaScript**, so every React-side lever had already been pulled and what was left was style, layout and paint for ~10 elements per column row. The hard ceiling was zoom: a composited layer re-rasterizes its whole content whenever the transform SCALE changes, so a wheel gesture repainted 2.25 screens of DOM every frame. It arrived as a field report — "above 70% zoom it lags, below 70% it is fine" — 0.7 being exactly `LOD_NAMES_BELOW`, where the `full` level starts. A canvas removes style and layout entirely and turns paint into blits.
  - **A card is rendered ONCE into an offscreen bitmap and blitted after that** (`erCardRenderer.ts`). Everything else follows from that sentence:
    - **The raster scale is not the zoom.** `quantizeRasterScale` snaps it to ~√2 steps and it is re-evaluated only when a gesture SETTLES, so a wheel burst re-uses the bitmaps it has and the cards go slightly soft for a moment rather than every visible card re-rendering per frame. This is the trade a map renderer makes with tiles, and it is the single decision that makes zooming cheap — do not make it follow the live zoom.
    - **The cache is capped in BYTES, not entries** (64MB, LRU). A card at raster scale 2 is ~400KB, so a few hundred of them is half a gigabyte; an entry count cannot express that, and the cards it would keep are the cheap ones.
    - **`blocks` is deliberately NOT cached, and it has its own draw function** (`drawBlockCard`, not `drawCard` with the body skipped). At that zoom a card is a filled rectangle, cheaper to draw than to look up, and it is the one level where fit-to-view puts thousands on screen at once — where a bitmap per card would be a memory disaster rather than a saving. It is also the level where anything invisible is invisible **two and a half thousand times**: sharing `drawCard` meant a `save`/`clip`/`restore` to paint the header band and a `measureText` + ellipsis fit + `fillText` for a title 0.36px tall, per card, per frame — measured at **23ms average / 43ms worst** on a 2514-card, 4499-connector frame. `blockCardDetail(zoom)` gates both by legibility: the corner radius below ~1.5 device pixels, the title below ~5px. Two fills, and a `fillRect` rather than a ten-segment path when the rounding cannot be seen.
    - **A frame may render at most `CARD_FILL_BUDGET` new bitmaps**, draws the rest as skeletons and reports itself incomplete so the caller draws again. Without it, one frame can be asked to render every card it can see — fit-to-view, a theme switch, a detail-level change — which is the stall this renderer exists to remove.
    - A theme switch invalidates the cache through `ERPalette.id` (keyed on `data-theme`), so there is no explicit invalidation to forget; the cache is *also* cleared outright, because stale bitmaps still hold their bytes. Web fonts are the one change no attribute describes — until `document.fonts.ready`, `fillText` bakes the fallback family into a bitmap for the life of the tab, hence `invalidateErPalette()`.
  - **`erTheme.ts` is the only place the canvas learns a colour.** `getComputedStyle` flushes style, so it runs once per theme and never inside a frame or a card render. Changing a `--win-*` token still changes the diagram; adding a CSS rule for a card does nothing, because there is no element for it to match.
  - **A gesture never renders, and now neither does a pan.** `viewportRef` is the only viewport — the committed snapshot, `needsRecommit()` and `CULL_MARGIN` went with the mounted set they existed to stabilize. Pointer, wheel and tween handlers write the ref and ask for a frame; `flush()` runs a queued frame when the pointer comes up, so what gets saved is the position on screen and not the previous frame's. A node drag writes `positionsRef` directly each frame and tells React once, on release — and the sync effect **must not** overwrite `positionsRef` while that drag is in flight (`gestureRef.current?.kind !== 'node'`), or a render landing mid-drag puts the pre-drag positions back under the pointer.
  - **Hit testing is geometry, not the DOM.** `hitTestCards` walks the positions in REVERSE draw order, because the topmost card is the one drawn last. `hitTestRelationships` flattens each curve into 14 segments and **must** be culled to the screen first: resolving a connector's sockets calls `getColumnSocketPosition`, which scans the table's columns by name, so uncelled it is O(relationships × columns) on every pointer move — six figures of string comparisons per mouse movement at 5000 FKs. `document.elementFromPoint` is gone, and with it the forced layout it caused.
  - **A connector is culled by where its LINE goes, and by two different tests.** Testing the bounding box of its two tables looks equivalent and is not: a connector between tables half a diagram apart has a box that overlaps every viewport there is — measured on 2500 tables / 4998 FKs at 85% zoom, the box test passed **all 4998** and `connectorIntersects` (the honest segment) 600. Which of the two honest tests to use depends on the zoom, and the canvas rewrite got this wrong once: `connectorHasVisibleEnd` was deleted on the argument that a connector is now just a few segments in a batched `Path2D`, and `__erPerfDebug` then showed **176 connectors drawn against 7 visible cards at zoom 1.00** — ~140 dashed lines crossing the view with both ends, both sockets and the arrow head off screen, each still costing two socket resolutions, a curve, two arcs and an arrow head. So: endpoint test at `full`/`names`, where such a line says nothing; segment test at `blocks`, where those diagonals ARE the shape of the graph and a connector is two points. `connectorIntersects` is conservative by construction (the curve stays inside the centre-to-centre segment grown by half a card plus the bezier reach), so nothing visible is ever culled.
  - **At `blocks` a connector is a straight `lineTo`, not a bezier** — which is what the old flattened SVG path drew too. The bow is at most 180 world units, under a device pixel down there, and skipping it saves both the control-point object and the curve flattening the rasterizer does per path, 4499 times in the fit-to-view frame.
  - **Connectors are drawn as SIX batched paths, not four draws per connector** — curves, sockets and arrow heads, each split plain/lit — so the whole layer is a fixed handful of submissions however many foreign keys are on screen. A canvas path costs what it costs to submit far more than what it holds, and at `full` a couple of hundred visible connectors had been ~750 `beginPath`/`fill`/`stroke` calls per frame. The dash pattern is the other reason to batch: dashing makes the rasterizer flatten every curve and lay out every dash along it. Sockets and arrow heads exist **only** at `full`, where both are still over a device pixel. The lit batch strokes at `2.5 / zoom` so it stays readable at any zoom, which is what `vector-effect: non-scaling-stroke` used to do.
  - **Nothing the frame loop can hoist may stay in it, and "it is only a `Map.get`" is not an argument at sixty frames a second.** Three of these were the difference between "smooth" and "smooth but sluggish", which is a latency symptom and reads nothing like the frame drops that motivated the rewrite: (1) `resolveRelationships` looks both tables of every FK up ONCE, when the catalog or a filter changes — per frame it was 20,000 lookups at 5000 FKs; (2) `getColumnSocketPosition` resolves its row through a `WeakMap`-cached index instead of `visibleColumnsOf(...).findIndex(...)`, which allocated a lower-cased string per column per socket per frame plus a filtered array per call at the non-`full` detail levels — thousands of short-lived strings a frame, not slow enough to drop one but enough garbage to feel sticky, and the one `toLowerCase` per CALL that survived that fix is memoized too, because at fit-to-view it is still ~9,000 allocations a frame; (3) the batching above. Hover is what makes this matter: with no retained scene, moving the pointer across a card boundary repaints everything, so the frame cost IS the pointer's responsiveness.
  - **`window.__erPerfDebug = true` in DevTools** logs frame count, average and worst frame, cards and connectors drawn, bitmaps rendered, cache size, zoom and raster scale — once a second, as one flat string (DevTools collapses objects behind `Array(4)`, and the collapsed fields are the ones worth reading). Same convention as `window.__sqlCompletionDebug`. Reach for it before theorising: the fixes above came from reasoning about the code, and the next round should come from the numbers.
  - **Level of detail is chosen from the zoom, and the thresholds are legibility, not cost** (`full` where 11.5px type text still renders at 8px). What a level costs moved when cards became bitmaps: it is paid once per card per raster generation, not once per frame. **Heights never change between levels** — a card keeps what `calculateNodeDimensions` gave it — because the FK sockets anchor at `y + HEADER_HEIGHT + index * ROW_HEIGHT`, so a level that drew fewer rows would shrink the card out from under its own connectors.
  - **Hover and selection are two `Set`s the painter reads, not classes on elements.** `recomputeLit()` builds them and the frame dims everything outside with `globalAlpha`. The old `applyHighlight()` had to re-assert `hl` after every commit because culling remounted cards without it; there is nothing to re-assert now.

Hover hit-testing is skipped entirely for the hand tool, and skipped over the floating panels: their pointer events bubble to the container, and without the check, moving across the toolbar lights up whichever table happens to sit under it.

  - `computeBezierControls` is the single definition of the curve: the painter needs the numbers (`bezierCurveTo`, the arrow head's tangent, hit testing) and `erExportHelper.ts` needs the path string. A second copy would drift and an exported diagram would stop matching the one on screen. The export is otherwise untouched by all of this — it has always built SVG from **data**, never from the live DOM.
  - **`computeAutoLayout` lays the diagram out as one block per MODULE, not as one layered graph** — and the route to that is worth more than the result, because two plausible designs were measured and rejected on the way. All numbers are from `scripts/make-er-mock-db.mjs`-shaped schemas (~79% of foreign keys inside a module), reading the median connector length and how many connectors a centred viewport mounts at 85% zoom:
    - *Layering alone*, which is what it did originally: it ran step one of Sugiyama and then placed each layer in whatever order a `Set` iterated in, so two tables sharing a parent could sit at opposite ends of a column. It also had a `nextLayerSet.size < 6` escape hatch that let a table into a layer before its parents, which did not merely tolerate FK cycles but **created** long backwards edges in schemas that had none. `breakCycles` (DFS back-edge removal) replaced it.
    - *Adding barycentric ordering across the whole diagram* — the textbook fix, and it under-delivered: median −12%, mean −5%. The reason is the **column height budget**: keeping a few hundred tables screen-shaped forces each layer to wrap into several columns, and once a layer wraps, a table's index within it is no longer its y coordinate — which is the one assumption barycentric ordering rests on. The wrap was quietly cancelling the ordering.
    - *One block per module, layered inside it*, which is what ships: median **−7% at 320 tables and −37% at 1200**, connectors mounted at 85% zoom **−53% and −31%**. A module is small enough to need little or no wrap, so inside a block the ordering means what it says. What is given up is that the left-to-right FK reading is now per module rather than diagram-wide — which is where it was being read anyway, since nobody traces a foreign key across thirty columns.
    - Finding the blocks was **not** community detection. Label propagation is the textbook answer and it collapses: labels update in place in a fixed order and ties go to the smaller one, so the alphabetically smallest label sweeps the graph — it returned ONE community of 1200 on a schema with 79% intra-module edges, and a seeded shuffle only makes it unstable rather than correct. Layout does not need true communities, it needs a partition into workable blocks with most edges internal, and stated that way `partitionIntoBlocks` is greedy size-capped growth: busiest table left, then whichever neighbour has the most edges into the block. **Fill every block to the cap even after its frontier runs dry** — ending it there fragmented 320 tables into 70 blocks of four instead of 12 of 27, which inflated the diagram by the gaps, lengthened the mean connector, and made `orderBlocks` quadratic over hundreds of entries (183ms at 2500 tables, now 32ms).
    - `TARGET_ASPECT` for the shelf packing is 2.2, above a screen's own 1.78 because ragged rows come out squarer than asked. At 1.5 the packing was handing back the entire screen-shape win: fit-to-view zoom 0.081 against 0.122.
    - The column budget itself still applies, now per block: solving `columns * pitch = stack / columns` keeps a block from being a ribbon, and the 1200px floor leaves a small diagram laid out one layer per column exactly as before. Tables with **no** foreign key are packed into a grid of their own after the flow — sharing layer 0 with the real root tables, they used to stretch its first column for no reason.
  - Layout is **derived state reconciled in the render pass**, not in an effect — an effect would paint the previous layout for one frame, which at this size is a visible jump of every card. It is keyed by `erLayoutKey(connKey(config), database, schema)`: keying on `conn_id` meant a fresh UUID per connect, so a hand-arranged diagram was never found again and localStorage grew one dead entry per session.
  - The minimap shows the viewport by **dimming what is outside it** (an SVG mask) rather than painting a slab over the node rects — which also removes the clamping that turned the indicator into a two-sided corner whenever the viewport reached past the diagram edge. No `backdrop-filter`: it sits on top of the diagram, so a blurred backdrop means reading those pixels back every time any of them repaints.
- `sql/` — everything that makes the SQL editor "smart". Split from `SqlEditor.tsx` so each piece is separately replaceable, and so the pure-text ones stay testable:
  - `sqlLanguage.ts` — wires `monaco-sql-languages` (ANTLR parser per dialect) to the app's catalog via a `completionService`: keywords from the parser, tables/columns from `catalog.ts`, alias-scope awareness, `JOIN ... ON` conditions derived from foreign keys, `*` right after `SELECT`, dialect snippets, and usage-frequency ranking (`usageStats.ts`). It also completes **column values** at `WHERE col = `, `IN (` and `LIKE ` — but only from what the catalog already holds: MySQL returns `COLUMN_TYPE`, so `enum('active','banned')` carries its own value list, and a BOOLEAN has two. **No query is ever sent for this**, which is also why `WHERE id = ` correctly suggests nothing — an `int` has no value set to list, so it falls out without a special rule. Extending this to `SELECT DISTINCT col FROM t` is deliberately not done: that is a full table scan triggered by a keystroke, and on a production connection it stops being a suggestion and becomes an incident. **Right after `JOIN` it also ranks the table list**: a candidate the FK graph connects to a table already in scope is promoted to the `1z_` tier, labelled with the condition, and — unless an `ON` already follows the caret — inserted WITH its `ON` clause (`JOIN address a ON a.city_id = c.city_id`). That pass reads `catalog.getCachedSchema()` only, so the ranking itself costs no IPC — the one thing it awaits is `ensureCatalogPrimed()`, because the first `JOIN` of a session is exactly when the cache is still cold and the ranking would silently do nothing. It is also `fkOnly`, because the same-name fallback `buildJoinConditions` uses at the caret would call every table joinable in a schema where each one has an `id`, and a ranking that promotes everything ranks nothing. `LANG_IDS` lists the three language ids in use (`mysql`, `pgsql`, `genericsql` — the last one covers SQLite).
  - `catalog.ts` — cached table/column/FK metadata for completion+hover (one `get_full_catalog` call warms it — two or three queries on **every** dialect now, including SQLite, which has no `information_schema` but does expose `pragma_table_info`/`pragma_foreign_key_list` as table-valued functions; it used to return empty there and leave the frontend calling `get_table_schema` per table, which the ER diagram turned into a few hundred round trips before its first frame). `invalidateCatalog()` on connection change, DDL, rename and restore; `getCachedSchema()` is the no-backend read used on paths that may scan every table, and `ensureCatalogPrimed()` awaits the bulk prime for the one caller whose ANSWER depends on it (the FK ranking after `JOIN`) — capped by a timer, with the prime left running past the cap, so a slow connection costs one unranked popup rather than a popup that hangs.

That last one exists because `collectTableRefs()` cannot tell a CTE from a table — it sees `FROM recent` and reports a table named `recent`, which `inspection.ts` then fails to find in the catalog and underlines in red on a perfectly valid `WITH recent AS (…)`. Any new check that resolves a `FROM`/`JOIN` name against the catalog has to subtract it, the same way it subtracts `DUMMY_TABLES`.
    - **Do not trust the ANTLR entities alone for alias scope.** Three independent ways the parser leaves us with no scope while the user is mid-typing:
      1. It is wrong in dialect-specific ways — measured: for `… JOIN address a on ` the Postgres parser omits the freshly joined `address`, and for `… on c.` the MySQL parser returns *zero* entities.
      2. `monaco-sql-languages` only computes entities at all when `suggestions.syntax` is non-empty (`baseSQLWorker.js`, `doCompletionWithEntities`) — otherwise it hands us `allEntities: null`.
      3. `getSuggestionAtCaretPosition()` returns `null` outright when the parse tree or caret token cannot be resolved, so `suggestions` itself can be null.
      Losing the alias map makes column completion fall back to "every table" and silently disables the FK-based `JOIN … ON` suggestion. `sqlLanguage.ts` therefore merges the parser entities with `collectTableRefs()` over the statement under the caret (entities win when present), and on a null `suggestions` it keeps going in a degraded mode — inferring table-vs-column from the text — instead of returning nothing. `collectTableRefs()` keeps source order because the JOIN-condition builder needs to know which table was joined last.
    - `joinConditions.ts` holds the FK/name-based `JOIN … ON` builder, **no monaco import**, with `getSchema` injected so it is unit-testable (see `joinConditions.test.ts`).
    - Set `window.__sqlCompletionDebug = true` in DevTools to have the completion service log its decisive inputs (`inOnClause`, `scopeTables`, `entityTables`, `joinConds`, `parserFailed`, `syntax`) on every keystroke. Completion depends on both the parser and live DB metadata, so this is usually the fastest way to find which link is missing — and note that a correct `joinConds` in the log with nothing visible in the popup means the problem is Monaco's *ordering*, not this file. It logs **one flat string** rather than an object on purpose — DevTools collapses nested values behind `Array(4)`/`…`, so copying the console out of the app used to drop `joinConds`, the one field most worth reading; keep it flat when editing. The `no viable alternative` / `extraneous input '<char>' expecting {…}` lines the ANTLR worker prints on incomplete SQL are expected noise, not the failure — they come from `dt-sql-parser`'s `getAllEntities` inside the web worker and don't stop completion (the next `[sql-completion]` line still logs a full scope).

    - **`snippetSuggestions` must stay `'inline'`.** Suggestion order lives entirely in `sortText` (`00_` star/expand-columns and column values, `0_` FK JOIN condition, `1_` column, `1z_` a table the FK graph says is joinable to what is already in scope, `2_` table, `3_` in-scope table name, `3t_` live template, `4_`/`5_` keyword, `z_` dialect snippet — `1z` and not `15`, because `'5' < '_'` would put it ABOVE the columns). `'bottom'`/`'top'` makes Monaco group every `kind: Snippet` item at one end and **ignore its sortText** — that silently buried the JOIN-condition and "list N columns" suggestions dozens of rows down. `completionOrder.test.ts` pins both the tier order and this option.
  - `intellisense.ts` — hover (table → column list, column → type/PK/FK) and Ctrl+Click / F12 "open this table", which dispatches the `open-table-tab` `CustomEvent` handled in `App.tsx`.
  - `inspection.ts` — the squiggles: unknown table, unknown `alias.column`, and (per statement) unqualified columns in the select list — missing from every table in scope, or **ambiguous** because more than one of them has it. Two more: a comparison against a literal of the wrong type family, and a select-list column that is neither grouped nor aggregated. Two rules run through all of it. First, **silence beats a wrong warning**: a false positive teaches the user to ignore every underline including the true ones, so each check bails out entirely when the scope is not fully known — a CTE, a derived table in `FROM`/`JOIN` (where `collectTableRefs` reports the *inner* query's tables), an unknown table, no `FROM`. Second, a check whose answer depends on the dialect takes `inspectSqlText(text, dialect)` and does nothing when it is absent, rather than assuming one: ambiguity is a hard error on MySQL/Postgres but perfectly legal on SQLite, which just takes the first match. The dialect is the Monaco language id, read off the model in `runMonacoInspection` — free, and always right for the pane.
  - `outline.ts` — the Outline panel / breadcrumb and per-statement folding, both reading `splitStatements()` so there is no second notion of where a statement ends (it already handles `$…$`, `DELIMITER` and trigger bodies). Names come from `describeStatement()` in `statements.ts`, which finds the first verb at **paren depth 0** on the masked text — so a verb inside a string, a comment or a subquery cannot steal the label — and walks past `WITH`, because labelling every CTE query "WITH" makes them indistinguishable in a list. Folding matters more here than in most languages: Monaco falls back to indentation folding, and SQL is largely unindented, so without a provider the fold arrows are close to useless.
  - `signatureHelp.ts` / `peekDefinition.ts` — parameter hints while typing a call, and Alt+F12 to read a table's DDL inline. Both keep their fallible part elsewhere: signature help gets its text from `docsService` (the same table hover and completion read, so there is no second copy to drift) and its only computation, "which call am I inside and which argument", is `enclosingCall()` in `statements.ts` — pure and tested, including that the function name must touch the `(`, since `SELECT (a + b` would otherwise pop up `SELECT`'s own syntax entry. Peek needs a *location in a model*, and a table has no source file, so it builds a virtual `tablegrid://table/<conn>/<name>.sql` model — keyed by connection because two connections both having `users` are two different definitions — from `get_table_definition`, falling back to a DDL synthesised from the cached catalog when the backend cannot answer. **Alt+F12 is deliberately not F12**: Ctrl+Click and F12 still open a table tab (the hover text promises exactly that), and glancing at a structure is a different intent from opening the data.

(2) **Statement-level built-ins are gated by `atStatementStart`** (nothing since the last `;`, or right after `(`): without it `del` + Tab in a WHERE, which used to complete the keyword, drops a DELETE block into the statement. (3) Placeholder 1 is the table wherever there is one, so table completion is what shows first; `ij`/`lj` end right after `ON`, where the FK join conditions appear.
  - `quickFix.ts` — the Ctrl+. code actions for `inspection.ts`'s squiggles. It re-runs `inspectSqlText` rather than reading `context.markers`, because a marker carries only the **translated** message and recovering an identifier from it would break the moment the language changes — the same rule as "never branch on user-facing text". The suggestions behind it come from `dbIndexRegistry`'s `findSimilarColumns`/`findSimilarTables`, which match by substring **and** Damerau–Levenshtein distance: plain substring matching found `emai` → `email` but never `nmae` → `name`, i.e. it missed the transposed-key typo that a "did you mean" exists to catch.
- `i18n/` — localization (English / Vietnamese / Japanese) via `react-i18next`. Initialized by a side-effect `import './i18n'` in `main.tsx`, which covers both the main window and the standalone terminal window (`?term=`). See `docs/implementation_plan2` for the rollout. **The migration is complete**: every component, every error thrown from `src/utils/`, and every message returned by the Rust backend now reaches the user in the active language. Adding a new user-facing string anywhere in `src/` means adding a key, not a literal.
  - `locales/en.ts` is the source of truth for the key tree; `vi.ts`/`ja.ts` are declared `typeof en`, so a missing or misspelled key is a **compile error**. `i18next.d.ts` augments `CustomTypeOptions` so `t('…')` call sites are type-checked too — never introduce a dynamic key (`t(\`a.${x}\`)`), use a `switch` returning literal keys.
  - Placeholders are named `{{n}}`, **never `{{count}}`** — `count` puts i18next into plural mode and would demand `_one`/`_other` siblings per language.
  - Strings containing `<strong>`/`<code>` are rendered with `<Trans>` so each language keeps control of word order; `__tests__/locales.test.ts` fails the build if a translation drops a placeholder or a tag.

  - Watch for `t` shadowing when localizing a new file: callbacks like `.map(t => …)` must be renamed, or the translation function is hidden.   - A memoized callback that feeds an effect must read `t` through a ref, not directly: `t` gets a new identity on every language switch, so a direct read makes the effect re-run. `DataGrid.tsx`'s `fetchSchema` does this because its effect clears the unsaved-edit buffer; `SqlEditor.tsx` does it for the Monaco action labels. Where a ref does not fit, the effect carries an `eslint-disable-next-line react-hooks/exhaustive-deps` with the reason (`ConnectionManager.tsx`, `DatabaseInfoModal.tsx`).
  - Numbers and dates use `toLocaleString(i18n.language)` — do not hardcode `'vi-VN'` again.
  - Never branch on user-facing text (`msg.startsWith('Đang')`); keep a separate boolean. `SchemaMigration.tsx` had exactly this bug before the migration.
  - `TerminalPanel.tsx` writes into the xterm buffer, which holds bytes rather than React nodes: text already printed is **not** re-translated on a language switch, only new output is. Its shell-opening effect therefore reads `t` through a ref — putting `t` in that effect's deps would tear down the live PTY.
  - Plain modules under `src/utils/` have no hook, so they `import i18n from '../i18n'` and call `i18n.t(...)` on the shared instance. This works under Vitest's `environment: 'node'` — the language detector no-ops without `window`, so tests resolve to the `en` fallback. `src/sql/statements.ts` deliberately imports nothing, keeping the property described above.
  - **Rust error messages are translated at the `dbHelper` boundary, not in Rust.** `src/utils/backendErrors.ts` maps the ~55 Vietnamese messages from `src-tauri/src/*.rs` to the `backend` namespace (38 whole-message entries + 21 regex rules that translate the framing and pass the interpolated driver text through). It is the twin of those Rust literals in the same way `src/sql/statements.ts` is the twin of `split_sql_statements` — **reword a message in Rust and you must update the table**. `src/utils/__tests__/backendErrors.test.ts` enforces a byte-identical Vietnamese round-trip, and unmatched text passes through unchanged so nothing is ever lost. `dbHelper.ts` gets this for all 63 call sites from one local `invoke()` that shadows the imported one; it rethrows a **string**, not an `Error`, because the surrounding `catch` blocks interpolate `${err}` directly.
  - Do not localize a string that doubles as a lookup key. `queryParamHelper.ts` generates `?#N` for positional parameters (stable, persisted in `localStorage`) and builds the visible label from it at render time via `positionalParamIndex()` + `queryParams.positionalParam`.

### Build/config notes

- **Monaco is loaded lazily, and three separate things keep it that way — breaking any one of them silently puts 4MB back into startup.** `SqlEditor` (`App.tsx`), the Redis `Console` (`RedisToolTab.tsx`) and `RowDocumentModal` (`DataGrid.tsx`, its JSON tab) are the app's three edges to `monaco-editor`; all three are `React.lazy`, so **a static import of any of them — or of anything that imports `monaco-editor` — from a module the entry reaches undoes it for all of them.** That is exactly how it broke once: `RowDocumentModal` was imported statically by `DataGrid`, which put the 4.1MB `monaco` chunk back into the startup `modulepreload` list and grew the entry chunk from 836kB to 1,333kB — with nothing failing, so only the build output showed it. (1) `vite-helpers` must stay the **first** `codeSplitting.groups` entry: `__vitePreload` exists only because of those dynamic imports, and rolldown otherwise parks that ~1kB helper inside a big group chunk, which the entry then statically imports. (2) `react-vendor` must come **before** `monaco`: `@monaco-editor/react` is CJS and drags a CJS copy of `react/jsx-runtime` with it, and whichever group claims that copy is the chunk the entry's JSX binds to. (3) The worker factory lives in `src/sql/monacoSetup.ts`, not in `SqlEditor.tsx`, because either lazy chunk can now be the first to touch Monaco and both must find a configured `MonacoEnvironment`. That module lists **only** the three SQL dialect workers plus the generic editor worker — Monaco's json/css/html/typescript workers are deliberately not imported; nothing here opens a model in those languages, and each `?worker` import emits its chunk whether it runs or not (`ts.worker` alone was 5.9MB, the largest file in the build). Verify with `dist/index.html` after `npm run build-frontend`: the `monaco` chunk must **not** appear as a `modulepreload`.
- `vite.config.mts` pins the dev server to port `5173` (`strictPort: true`, matching `devUrl` in `tauri.conf.json`) and ignores `*.db`/`*.sqlite`/`*.dump`/`*.gz`/`*.sql` files from its watcher so local test databases don't trigger reloads.
- Tauri capabilities are minimal (`src-tauri/capabilities/default.json`): `core:default`, `dialog:default`, `fs:default` — extend this file if a new command needs a broader permission.
- Cargo edition 2024; DB drivers are `rusqlite` (bundled SQLite) and `sqlx` (Postgres + MySQL via `runtime-tokio` + `tls-rustls`).
- Fonts are **bundled**, not fetched: `public/fonts/` holds Inter (variable) + JetBrains Mono (400/500/600/700 + italics), declared as `@font-face` at the top of `src/index.css` with the OFL licenses alongside them. Do not reintroduce a Google Fonts `<link>`/`@import` — the app must render correctly offline. Neither bundled family has CJK coverage, so `--win-font-sans`/`--win-font-mono` end with OS CJK fallbacks (Yu Gothic UI / Hiragino Sans / Noto Sans JP / Meiryo) for the Japanese locale; those are system fonts, so offline rendering still holds — keep them when editing the stacks. When changing the editor font, keep `SQL_EDITOR_OPTIONS.lineHeight` and the `.sql-run-glyph::before` `line-height` in `index.css` in sync, or the gutter run-arrow drifts off-center.
